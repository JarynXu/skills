# AUDIT：资深产品审查

用于审查产品文档、产品定义或现有产品的逻辑和专业性。

## 12. AUDIT 模式

### 12.1 审查对象

审查的不只是 Markdown 结构，还包括：

- 产品目标；
- 用户问题；
- 需求链路；
- 业务对象；
- 流程；
- 状态；
- 权限；
- 数据；
- 异常；
- 验收；
- 技术和设计边界；
- 文档治理；
- 下游可执行性。

### 12.2 审查维度

#### 战略一致性

- 目标是否清楚；
- 目标是否源于真实问题；
- 功能是否支撑目标；
- 指标是否能验证目标；
- 范围是否符合优先级；
- 是否存在无依据功能。

#### 用户完整性

- 用户和角色是否完整；
- 各角色目标是否明确；
- 关键场景是否覆盖；
- 是否只覆盖了部分角色或单一视角；
- 是否覆盖首次、日常、异常和退出场景。

#### 产品逻辑

- 核心对象是否明确；
- 对象关系是否一致；
- 生命周期是否闭环；
- 状态是否可进入、可退出；
- 规则是否冲突；
- 例外是否被明确表达。

#### 权限与风险

- 谁能看什么；
- 谁能操作什么；
- 谁能修改谁；
- 敏感字段是否受保护；
- 高风险操作是否需要确认、审计和恢复；
- 最后一位所有者、自我删除等边界是否处理。

#### 数据与内容

- 输入和输出是否明确；
- 字段含义是否清楚；
- 校验是否完整；
- 术语是否统一；
- 通知是否定义触发、接收者和失败处理。

#### 异常与边界

至少检查：

- 初始；
- 空；
- 加载；
- 成功；
- 失败；
- 无权限；
- 数据不存在；
- 数据被删除；
- 过期；
- 重复提交；
- 网络中断；
- 外部依赖失败；
- 并发修改；
- 部分成功；
- 撤销；
- 恢复；
- 不可逆操作；
- 权限在操作中变化。

#### 可交付性

- UX 是否仍需猜业务逻辑；
- 架构是否知道要验证什么；
- 开发是否能确定系统行为；
- QA 是否能写客观测试；
- 验收条件是否可执行。

#### 文档治理

- 是否有唯一事实源；
- 是否存在重复和冲突；
- 是否有稳定 ID；
- 是否记录来源和状态；
- 是否可追踪变化；
- 是否存在巨型混杂文档；
- 是否将假设伪装成事实。

### 12.3 严重程度

#### Critical

会导致产品逻辑无法成立、产生安全风险，或阻塞下游：

- 核心目标不明确；
- 关键规则冲突；
- 核心状态模型缺失；
- 权限漏洞；
- 范围无法判断；
- 核心流程没有结束条件；
- 假设被当作事实。

#### Major

很可能造成返工或不一致：

- 异常流程缺失；
- 字段定义不完整；
- 术语不统一；
- 需求缺少来源；
- 验收标准不可测试；
- 功能与目标不可追踪。

#### Minor

主要影响维护性和专业性：

- 命名不一致；
- 章节组织不清；
- 重复描述；
- 链接、编号和导航问题。

### 12.4 审查问题模板

```md
## AUDIT-XXX 标题

Severity:
- Critical / Major / Minor

Evidence:
- 文件、章节、需求 ID 或观察结果

Problem:
- ...

Why it matters:
- ...

Downstream impact:
- UX / Architecture / Development / QA / Analytics / Operations

Required action:
- ...

Resolution type:
- Auto-fix / Product decision / Business confirmation / Architecture validation / UX exploration

Status:
- Open / In progress / Resolved / Accepted risk
```

### 12.5 双重质量结论

分别评价：

1. **Documentation Quality**：结构、归档、表达、追踪和维护质量。
2. **Product Definition Quality**：目标、用户、逻辑、规则和可执行性质量。

不得因文档排版漂亮、章节齐全或图表很多而给出高产品质量评价。
