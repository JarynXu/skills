# NORMALIZE 与 MAINTAIN

用于规范化旧资料、保留迁移历史，以及持续维护产品定义的一致性。

## 13. NORMALIZE 模式

### 13.1 目标

规范化不是重新排版，而是：

- 提取原始事实；
- 区分信息性质；
- 建立标准目录；
- 分离产品、UX 和技术内容；
- 合并重复定义；
- 建立稳定 ID；
- 建立唯一事实源；
- 标记冲突和缺失；
- 保持可审计的迁移历史。

### 13.2 安全规则

- 保留原始资料，不覆盖或删除来源。
- 不得擅自改变业务含义。
- 不得用常见做法填补未知规则。
- 不得将 UI 方案反推成已确认需求。
- 不得将技术实现反推成产品约束。
- 无法判断时创建 `[OPEN]` 或 `[CONFLICT]`。
- 将明确无语义变化的整理与语义变化分开记录。

### 13.3 规范化日志

每个迁移动作记录：

```md
## NORM-XXX

Source:
- 原文件和章节

Action:
- 移动、拆分、合并、重新分类、建立引用

Target:
- 新的权威文件和 ID

Semantic change:
- None / Description

Created open questions:
- OPEN-...

Created conflicts:
- CONFLICT-...
```

### 13.4 常见问题识别

主动识别：

- 背景、需求、方案和技术混在一起；
- 所有内容都写成“系统需要”；
- 巨型 `prd.md`；
- 重复规则；
- 相同术语含义不一致；
- 功能和目标断链；
- 只有正常流程；
- 对象生命周期缺失；
- 权限停留在页面级；
- 指标不可验证；
- 验收条件主观；
- 历史内容与当前内容混杂。

## 14. MAINTAIN 模式

### 14.1 更新原则

每次产品变化都应检查：

- 是否影响目标和范围；
- 是否影响用户和场景；
- 是否影响对象关系；
- 是否影响状态；
- 是否影响权限；
- 是否影响跨功能规则；
- 是否影响 UX 输入；
- 是否影响架构输入；
- 是否影响验收和 QA；
- 是否影响指标和发布。

### 14.2 变更记录

重大变化记录：

- 日期；
- 变更内容；
- 原因；
- 决策来源；
- 受影响 ID；
- UX、架构、开发和 QA 的影响；
- 是否需要迁移、回滚或重新验收。

### 14.3 架构结论回写产品

当架构验证产生用户可见或产品范围影响时：

1. 在架构文档保留实现决策；
2. 在产品文档更新确定的能力边界；
3. 更新相关功能规格、规则和验收；
4. 更新 UX 输入；
5. 在变更日志中记录。
