# 信息治理与通用工作流程

用于判断信息性质、证据强度、稳定 ID、来源登记和权威事实源。

## 7. 信息性质与证据状态

不得把所有内容统一写成“系统需要……”。

对每条重要信息判断其性质：

- `[SOURCE]`：原始资料来源。
- `[OBSERVED]`：从现有产品或流程直接观察到的事实。
- `[EVIDENCE]`：可核查的数据、访谈或业务证据。
- `[FACT]`：已经确认的客观事实。
- `[NEED]`：用户需要完成的事情。
- `[REQUIREMENT]`：正式产品要求。
- `[RULE]`：业务规则。
- `[CONSTRAINT]`：不可忽略的业务、技术、合规或平台约束。
- `[DECISION]`：已确认决策。
- `[ASSUMPTION]`：暂时采用但未确认的判断。
- `[HYPOTHESIS]`：需要验证的产品假设。
- `[PROPOSAL]`：候选方案。
- `[TECH-PREFERENCE]`：技术倾向，但允许替代。
- `[TECH-PROPOSAL]`：待架构评估的技术建议。
- `[OPEN]`：未决问题。
- `[CONFLICT]`：不同来源或定义存在冲突。
- `[INFERRED]`：根据证据推导出的候选结论。
- `[ANOMALY]`：现有产品中可疑或不一致的行为。
- `[LEGACY]`：已知历史遗留。
- `[DEFECT]`：已确认缺陷。
- `[UNKNOWN-INTENT]`：无法确定是否符合原始意图。

### 7.1 证据等级

逆向重建和审查时，每条重要结论至少记录：

- Evidence：依据；
- Confidence：High / Medium / Low；
- Interpretation：解释；
- Verification status：是否已验证；
- Canonical status：是否已进入正式产品定义。

### 7.2 禁止自动升级

不得执行以下升级：

```text
用户随口建议
→ 已确认需求

当前系统行为
→ 正确业务规则

技术候选方案
→ 正式架构约束

Agent 推断
→ 已确认事实
```

只有在获得明确证据或决策后，才能更新状态。


### 7.3 反锚定规则

默认加载的技能规则和参考文件应以抽象分类、判断问题、检查表和占位结构表达。

不得把以下内容作为通用规则的默认示例：

- 具体技术、框架、厂商或产品名称；
- 具体业务领域、角色、对象或功能名称；
- 固定阈值、时限、容量、比例或性能结论；
- 可直接复制到项目中的完成版需求或决策；
- 暗示某一方案为默认正确答案的叙述。

模板中需要表达结构时，使用 `<PLACEHOLDER>`。占位符仅表示字段类别，不提供事实、结论或默认值。

## 8. 稳定 ID 规范

为可追踪信息分配稳定 ID。不要因标题修改而更换 ID。

建议前缀：

```text
SRC       资料来源
EVD       证据
PROBLEM   用户或业务问题
INSIGHT   洞察
HYP       假设
GOAL      目标
METRIC    指标
USR       用户或角色
NEED      用户需求
SCN       场景
OBJ       业务对象
PROCESS   业务流程
STATE     状态模型
REQ       产品需求
RULE      业务规则
CONSTRAINT 约束
DEC       决策
ASSUMP    假设记录
OPEN      未决问题
CONFLICT  冲突
RISK      风险
OBS       产品观察
ANOMALY   异常
AUDIT     审查问题
NORM      规范化动作
ARCH-IN   架构输入
UX-IN     UX 输入
AC        验收标准
```

ID 结构：

```text
REQ-<DOMAIN>-<NUMBER>
RULE-<OBJECT>-<NUMBER>
OPEN-<NUMBER>
AUDIT-<NUMBER>
```

尖括号内容是占位符，不得直接写入正式文档。

同一事实只在一个权威位置完整定义。其他位置使用 ID 引用，不复制出多个略有差异的版本。

## 9. 通用工作流程

### 9.1 检查现有仓库

开始前：

1. 阅读 `product/README.md`；
2. 检查已有目录和文档；
3. 查找是否已有同类事实源；
4. 阅读来源、决策、假设、冲突和变更记录；
5. 不得在不了解现状时创建重复文档。

### 9.2 登记来源

任何正式输入都应登记到 `source-register.md`：

- 来源类型；
- 来源位置；
- 作者或提供者；
- 日期；
- 版本；
- 可信程度；
- 适用范围；
- 是否仍有效。

### 9.3 三遍研读

处理资料时至少执行三遍：

1. **背景遍**：理解目标、用户、范围和环境。
2. **建模遍**：提取对象、流程、状态、权限、规则、字段和约束。
3. **审查遍**：寻找遗漏、冲突、假设、异常和下游阻塞。

### 9.4 分类和归档

对每条信息：

1. 判断信息性质；
2. 判断权威归属；
3. 创建或更新标准文档；
4. 分配稳定 ID；
5. 从其他文档建立引用；
6. 将未决、冲突和风险显式登记。

### 9.5 建立产品模型

至少检查是否需要建立：

- 用户与角色模型；
- 用户需求和场景；
- 业务对象模型；
- 业务流程；
- 状态模型；
- 权限模型；
- 数据和内容定义；
- 跨功能规则；
- 功能规格；
- 验收标准。

### 9.6 切换资深审查视角

完成作者工作后，暂停写作者视角，独立执行一次审查：

- 产品定义质量；
- 文档治理质量；
- UX 可接手程度；
- 架构可接手程度；
- QA 可接手程度。

### 9.7 修复和升级

- 可以安全修复的结构、引用、重复和明确表达问题，直接修复。
- 需要业务决策的问题创建 `[OPEN]`。
- 不同来源冲突创建 `[CONFLICT]`。
- 高风险问题进入 `product-audit.md` 和 `risks-and-dependencies.md`。
- 不得用推测填补关键产品事实。
