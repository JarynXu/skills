# 产品边界与下游交接

当技术或 UX/UI 方案混入产品定义，或存在真实跨专业交接任务时读取。边界依据决定责任和产品影响判断，不依据某个术语出现在哪类文档中。

## 决定责任

产品工作负责定义：

- 为什么需要改变、为谁改变以及期望取得什么结果；
- 业务对象、关系、生命周期、规则、权限和数据含义；
- 用户可见行为、结果、异常处置责任和不可违反的约束；
- 产品范围、成功判断和可测试的验收条件。

UX 负责在产品约束内决定任务和信息如何被组织、交互如何反馈与恢复，以及如何降低用户负担。UI 负责视觉层级、表现语言、组件视觉状态和视觉可访问性。架构与工程负责选择能够满足产品行为和约束的可替换实现。

产品可以提出候选方向或验证问题，但不得把其他专业的选择伪装成已经确认的产品事实。

## 判断技术信息是否属于产品层

技术信息只有在改变以下任一产品事实时才进入产品定义：

- 产品范围或可承诺能力；
- 用户可见行为、等待、可用性或失败结果；
- 业务规则、数据能力或验收条件；
- 安全、隐私、合规、成本或运营边界；
- 外部依赖和不可忽略的交付风险；
- 下游可行性结论导致的产品取舍。

产品层记录影响、约束、来源和待验证问题；存储、接口、算法、部署、并发机制、框架和基础设施等可替换实现留在技术权威位置。

## 技术信息状态

需要正式区分时使用以下状态：

| 状态 | 含义 |
|---|---|
| `[TECH-FACT]` | 已存在且可核查的技术事实 |
| `[CONSTRAINT]` | 已确认且不可违反的产品相关约束 |
| `[TECH-PREFERENCE]` | 存在倾向但允许替代 |
| `[TECH-PROPOSAL]` | 尚待评估的实现建议 |
| `[TECH-OPEN]` | 需要架构或工程验证的问题 |
| `[ARCH-DECISION]` | 已由适当 authority 确认的技术决定 |
| `[PRODUCT-IMPACT]` | 技术结论对产品范围、行为或验收造成的影响 |

只有 `[PRODUCT-IMPACT]` 及其必要来源需要回写相关产品定义；详细技术决定仍由技术文档维护。

## 从方案表达恢复产品要求

输入直接指定界面、交互或技术实现时：

1. 判断它是外部承诺、不可变约束、已确认决定，还是候选方案；
2. 提取它试图实现的用户结果、业务规则、信息要求或风险控制；
3. 将真正不可变的产品影响写成约束或验收条件；
4. 将可替换方案保留为候选，并把需要其他专业确认的问题交给相应 owner；
5. 不因方案已经存在或表达具体就假定其合理。

```text
<SOLUTION EXPRESSION>
→ <INTENDED OUTCOME OR RISK>
→ <PRODUCT BEHAVIOR AND CONSTRAINT>
→ <DECISION LEFT TO THE OWNING DISCIPLINE>
```

## 交接触发条件

仅在同时满足以下条件时建立交接内容或交接文件：

- 存在明确接收方；
- 接收方需要当前产品信息作出决定或开始工作；
- 已有权威输入可以传递；
- 需要保留的约束、开放问题或验收边界超出当前对话。

读取本 reference、判断某专业未来可能参与，或目录中存在 `10-handoffs/`，都不构成交接触发条件。

## 交接契约

每次真实交接应让接收方知道：

- 交接目的和需要完成的决定；
- 适用范围、用户、场景和期望结果；
- 必须遵守的产品规则、状态、权限、数据含义和约束；
- 哪些内容已经确认，哪些是候选、假设、冲突或未知；
- 接收方拥有的设计空间；
- 需要返回产品定义的结论及完成证据。

不同接收方只接收完成其工作所需的部分，不复制整套产品定义。

## 准备度判断

准备度按接收方将要作出的决定判断：

- UX 不应再猜关键用户结果、业务规则、状态、权限和不可变约束；
- 架构不应再猜产品能力、规模目标、外部依赖、风险和需要验证的问题；
- 开发不应再猜产品可观察行为和规则优先级；
- QA 不应再猜完成条件、关键状态、权限和风险处置；
- 数据与运营不应再猜指标含义、责任边界和运行结果。

未满足的内容可以形成明确阻塞项；不要为了宣称准备就绪而补写未经确认的事实。
