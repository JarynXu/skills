# 产品边界与下游交接

识别到跨专业边界、技术影响、解决方案混入产品定义，或准备向 UX、UI、架构、数据和 QA 交接时读取。

## 15. 产品与技术边界

### 15.1 判断原则

技术信息是否进入产品定义，不取决于它是否包含某个技术名词，而取决于它是否会影响：

- 产品范围；
- 用户可见行为；
- 业务规则；
- 数据能力；
- 性能、等待和可用性；
- 安全、隐私和合规；
- 成本、交付和运营；
- 外部依赖；
- 验收标准；
- 下游设计空间。

只记录这些影响、约束和待验证问题。不要在产品文档中展开可替换的具体实现。

### 15.2 产品层应记录的内容

产品层可以记录：

- 已存在且不可忽略的技术事实；
- 已确认且不可违反的环境、平台、部署、数据或集成约束；
- 技术能力对产品范围和用户行为造成的边界；
- 需要架构或工程验证的可行性问题；
- 已由架构确认、且会改变产品行为或验收标准的结论；
- 需要向下游明确传递的依赖、风险和限制。

### 15.3 产品层通常不应规定的内容

以下内容通常属于架构或工程设计：

- 存储结构和数据模型实现；
- 接口协议、路径和内部契约；
- 缓存、队列、索引和调度机制；
- 框架、中间件和基础设施选型；
- 服务拆分、部署拓扑和扩缩容实现；
- 具体算法、查询和并发控制方式；
- 可在不改变产品行为的情况下替换的实现细节。

若某项实现已成为外部承诺、合同条件或不可变约束，只在产品层登记其约束性质和产品影响，详细方案仍由技术文档定义。

### 15.4 技术信息分类

遇到技术相关内容时，必须先分类：

- `[TECH-FACT]`：已存在的客观技术事实；
- `[CONSTRAINT]`：已确认且不可违反的约束；
- `[TECH-PREFERENCE]`：存在倾向，但允许替代；
- `[TECH-PROPOSAL]`：尚待评估的实现建议；
- `[TECH-OPEN]`：需要架构或工程验证的问题；
- `[ARCH-DECISION]`：架构阶段已经确认的技术决策；
- `[PRODUCT-IMPACT]`：技术结论对产品范围、行为、规则或验收造成的影响。

不得把偏好、建议或待验证项自动升级为硬约束或正式架构决策。

### 15.5 去实现化转换

当输入混入具体实现时，按以下步骤处理：

1. 识别该实现表达背后的目标、约束或风险；
2. 提取用户可见结果、业务规则和验收要求；
3. 将可替换的实现细节移出产品正文；
4. 将未确认的技术问题登记为架构输入；
5. 架构结论产生后，只将产品影响回写产品定义。

转换结构：

```text
<具体实现表达>
→ <意图或约束>
→ <产品行为与验收要求>
→ <需要技术确认的问题>
```

该结构只是分类协议，不代表任何默认技术、业务领域或产品结论。

### 15.6 技术约束的归档与引用

技术约束出现时：

- 在 `constraints-and-nfr.md` 定义约束及其产品影响；
- 已确认决策在 `decision-log.md` 登记决策事件；
- 风险进入 `risks-and-dependencies.md`；
- 需要技术处理的问题进入 `architecture-input.md`；
- 功能规格只引用约束 ID 和已经确认的产品能力边界；
- 不在多个文件复制同一约束的完整定义。

## 16. 产品与 UX/UI 边界

### 16.1 产品负责定义

- 为什么做；
- 给谁做；
- 解决什么问题；
- 需要提供哪些能力；
- 有哪些业务对象及关系；
- 状态如何变化；
- 规则、权限和数据边界；
- 输入和输出的业务含义；
- 正常、异常和边界行为；
- 不可改变的约束；
- 验收标准和成功判断。

### 16.2 UX 负责定义

- 用户如何完成任务；
- 信息如何组织；
- 任务流、页面流和交互结构；
- 反馈、恢复和错误处理体验；
- 如何降低认知负担；
- 在产品约束内探索更优解决方案。

### 16.3 UI 负责定义

- 视觉层级和界面表现；
- 字体、颜色、间距和图形语言；
- 组件视觉状态；
- 设计系统使用；
- 最终视觉一致性与可访问性呈现。

### 16.4 解决方案倒推检查

当输入直接指定页面结构、控件形式、布局位置或视觉表现时：

1. 判断它是不可变产品约束，还是候选设计方案；
2. 提取其背后的用户目标、业务规则和信息要求；
3. 没有需求依据时标记 `[UNJUSTIFIED-SOLUTION]`；
4. 不得把候选 UX/UI 方案升级为产品事实；
5. 将需要设计探索的问题写入 `ux-input.md`。

判断表：

| 问题 | 主要归属 |
|---|---|
| 定义用户最终获得的结果和业务行为 | 产品 |
| 定义业务对象、规则、状态、权限和约束 | 产品 |
| 决定任务如何被组织和完成 | UX |
| 决定页面、控件和交互方案 | UX |
| 决定视觉层级和界面表现 | UI |
| 决定可替换的技术实现 | 架构或工程 |

## 20. 下游交接标准

### 20.1 UX Readiness

UX 接手前应确认：

- 用户、角色和目标明确；
- 核心场景明确；
- 业务流程可理解；
- 对象和状态明确；
- 权限明确；
- 字段和内容要求明确；
- 异常和边界已覆盖；
- 不可改变的产品约束明确；
- UX 可探索的空间明确；
- 阻塞问题已登记。

### 20.2 Architecture Readiness

架构接手前应确认：

- 产品能力和范围明确；
- 数据规模、性能和可用性目标明确；
- 技术事实、硬约束、偏好和建议已区分；
- 外部系统、安全、隐私和部署要求明确；
- 待验证问题清楚；
- 不要求架构自行猜测产品行为。

### 20.3 QA Readiness

QA 接手前应确认：

- 需求具有稳定 ID；
- 业务规则明确；
- 状态和权限完整；
- 正常、异常和边界场景明确；
- 验收标准客观；
- 高风险场景已标记。
