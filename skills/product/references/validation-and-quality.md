# 验证、追踪与最终质量门槛

形成正式交付或声明工作完成前必须读取并执行。

## 18. 验收标准

验收标准必须：

- 客观；
- 可观察；
- 可测试；
- 与需求和规则关联；
- 覆盖正常、异常和边界。

不得使用：

- 体验良好；
- 合理处理；
- 视情况而定；
- 页面美观；
- 系统稳定；
- 尽快响应。

推荐格式：

```text
Given ...
And ...
When ...
Then ...
And ...
```

每条验收标准应关联需求、规则、状态和角色。

---

## 19. 追踪矩阵

维护完整链路：

```text
来源
→ 证据
→ 用户问题
→ 用户需求
→ 场景
→ 产品需求
→ 业务规则
→ 状态和权限
→ UX 设计
→ 架构决策
→ 验收标准
→ 测试用例
→ 成功指标
```

发现断链时：

- 标记未覆盖；
- 建立审查问题；
- 不得用伪引用掩盖缺失。

---

## 21. 禁止的低质量行为

严格禁止：

- 直接把用户原话改写成 PRD；
- 只描述正常流程；
- 只列功能名称；
- 凭空补充业务事实；
- 将假设写成已确认需求；
- 将当前产品行为自动视为正确规则；
- 将技术建议升级为硬约束；
- 将 UI 方案锁死为需求；
- 使用“合理处理”“视情况而定”等不可执行表述；
- 在存在冲突时擅自选择一方；
- 因资料不足跳过关键问题；
- 把未解决问题隐藏在正文中；
- 复制同一事实到多个文件；
- 根据项目大小采用简化目录；
- 为了文件少而混合信息类型；
- 为了显得完整而创建空文档；
- 把文档数量、排版和图表数量当作产品质量。

## 22. 完成前最终自检

### 22.1 战略

- 产品目标是否明确；
- 用户问题是否有依据；
- 功能是否支撑目标；
- 指标是否可验证；
- 范围和非范围是否明确。

### 22.2 用户

- 用户和角色是否完整；
- 用户需求是否以任务和结果表达；
- 核心场景是否覆盖；
- 是否遗漏低权限、内部和异常角色。

### 22.3 模型

- 核心业务对象是否明确；
- 对象关系是否一致；
- 生命周期是否闭环；
- 状态迁移是否完整；
- 流程是否有结束和失败路径。

### 22.4 规则和权限

- 规则是否可执行；
- 例外是否明确；
- 权限是否覆盖对象、操作、字段和数据范围；
- 高风险操作是否有保护和审计。

### 22.5 异常

- 空、失败、过期、重复、并发、部分成功是否处理；
- 外部依赖失败时是否有产品行为；
- 权限变化、撤销和恢复是否明确。

### 22.6 信息治理

- 每个事实是否有唯一权威位置；
- 来源、假设、决策、冲突和变化是否可追踪；
- 是否存在重复定义；
- 是否存在未显式标记的推断。

### 22.7 下游准备度

- UX 是否仍需猜业务事实；
- 架构是否仍需猜产品能力；
- 开发是否能确定系统行为；
- QA 是否能编写客观测试。

若任何关键项未满足：

- 不得宣布产品定义已完成；
- 创建明确的 `[OPEN]`、`[CONFLICT]`、`[RISK]` 或 `AUDIT` 记录；
- 标明阻塞的下游工作。

---

## 23. 输出原则

- 先更新事实源，再更新引用和交接。
- 先区分事实与推断，再表达结论。
- 先建立 As-Is，再建立 Canonical。
- 先定义产品行为，再讨论实现方案。
- 先完成作者工作，再切换审查视角。
- 能安全修复的直接修复；不能安全决定的显式登记。
- 目录结构必须长期稳定，内容随真实复杂度自然增长。

最终目标是建立一个即使产品从小变大、团队更换、历史信息缺失或文档长期腐化，也仍然能够持续维护和恢复的可信产品定义体系。
