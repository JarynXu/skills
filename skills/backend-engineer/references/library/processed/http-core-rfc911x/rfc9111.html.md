# HTTP Caching

## [1.](#rfc.section.1) [Introduction](#caching)

The Hypertext Transfer Protocol (HTTP) is a stateless application-level request/response
protocol that uses extensible semantics and self-descriptive messages for flexible
interaction with network-based hypertext information systems. It is typically used
for distributed information systems, where the use of response caches can improve
performance. This document defines aspects of HTTP related to caching and reusing
response messages.[¶](#rfc.section.1.p.1)

An HTTP cache is a local store of response messages and the subsystem that controls storage, retrieval,
and deletion of messages in it. A cache stores cacheable responses to reduce the response
time and network bandwidth consumption on future equivalent requests. Any client or
server *MAY* use a cache, though not when acting as a tunnel ([Section 3.7](rfc9110.html#intermediaries "Intermediaries") of [[HTTP]](#HTTP)).[¶](#rfc.section.1.p.2)

A shared cache is a cache that stores responses for reuse by more than one user; shared caches are
usually (but not always) deployed as a part of an intermediary. A private cache, in contrast, is dedicated to a single user; often, they are deployed as a component
of a user agent.[¶](#rfc.section.1.p.3)

The goal of HTTP caching is significantly improving performance by reusing a prior
response message to satisfy a current request. A cache considers a stored response
"fresh", as defined in [Section 4.2](#expiration.model "Freshness"), if it can be reused without "validation" (checking with the origin server to see
if the cached response remains valid for this request). A fresh response can therefore
reduce both latency and network overhead each time the cache reuses it. When a cached
response is not fresh, it might still be reusable if validation can freshen it ([Section 4.3](#validation.model "Validation")) or if the origin is unavailable ([Section 4.2.4](#serving.stale.responses "Serving Stale Responses")).[¶](#rfc.section.1.p.4)

This document obsoletes [RFC 7234](#RFC7234), with the changes being summarized in [Appendix B](#changes.from.rfc.7234 "Changes from RFC 7234").[¶](#rfc.section.1.p.5)

#### [1.2.2.](#rfc.section.1.2.2) [Delta Seconds](#delta-seconds)

The delta-seconds rule specifies a non-negative integer, representing time in seconds.[¶](#rfc.section.1.2.2.p.1)

```
  delta-seconds  = 1*DIGIT
```

A recipient parsing a delta-seconds value and converting it to binary form ought to
use an arithmetic type of at least 31 bits of non-negative integer range. If a cache
receives a delta-seconds value greater than the greatest integer it can represent,
or if any of its subsequent calculations overflows, the cache *MUST* consider the value to be 2147483648 (231) or the greatest positive integer it can conveniently represent.[¶](#rfc.section.1.2.2.p.3)

**Note:** The value 2147483648 is here for historical reasons, represents infinity (over 68
years), and does not need to be stored in binary form; an implementation could produce
it as a string if any overflow occurs, even if the calculations are performed with
an arithmetic type incapable of directly representing that number. What matters here
is that an overflow be detected and not treated as a negative value in later calculations.[¶](#rfc.section.1.2.2.p.4.1)

## [2.](#rfc.section.2) [Overview of Cache Operation](#caching.overview)

Proper cache operation preserves the semantics of HTTP transfers while reducing the
transmission of information already held in the cache. See [Section 3](rfc9110.html#terminology "Terminology and Core Concepts") of [[HTTP]](#HTTP) for the general terminology and core concepts of HTTP.[¶](#rfc.section.2.p.1)

Although caching is an entirely *OPTIONAL* feature of HTTP, it can be assumed that reusing a cached response is desirable and
that such reuse is the default behavior when no requirement or local configuration
prevents it. Therefore, HTTP cache requirements are focused on preventing a cache
from either storing a non-reusable response or reusing a stored response inappropriately,
rather than mandating that caches always store and reuse particular responses.[¶](#rfc.section.2.p.2)

The cache key is the information a cache uses to choose a response and is composed from, at a minimum,
the request method and target URI used to retrieve the stored response; the method
determines under which circumstances that response can be used to satisfy a subsequent
request. However, many HTTP caches in common use today only cache GET responses and
therefore only use the URI as the cache key.[¶](#rfc.section.2.p.3)

A cache might store multiple responses for a request target that is subject to content
negotiation. Caches differentiate these responses by incorporating some of the original
request's header fields into the cache key as well, using information in the [Vary](rfc9110.html#field.vary) response header field, as per [Section 4.1](#caching.negotiated.responses "Calculating Cache Keys with the Vary Header Field").[¶](#rfc.section.2.p.4)

Caches might incorporate additional material into the cache key. For example, user
agent caches might include the referring site's identity, thereby "double keying"
the cache to avoid some privacy risks (see [Section 7.2](#security.timing "Timing Attacks")).[¶](#rfc.section.2.p.5)

Most commonly, caches store the successful result of a retrieval request: i.e., a [200 (OK)](rfc9110.html#status.200) response to a GET request, which contains a representation of the target resource
([Section 9.3.1](rfc9110.html#GET "GET") of [[HTTP]](#HTTP)). However, it is also possible to store redirects, negative results (e.g., [404 (Not Found)](rfc9110.html#status.404)), incomplete results (e.g., [206 (Partial Content)](rfc9110.html#status.206)), and responses to methods other than GET if the method's definition allows such
caching and defines something suitable for use as a cache key.[¶](#rfc.section.2.p.6)

A cache is disconnected when it cannot contact the origin server or otherwise find a forward path for a request.
A disconnected cache can serve stale responses in some circumstances ([Section 4.2.4](#serving.stale.responses "Serving Stale Responses")).[¶](#rfc.section.2.p.7)

## [3.](#rfc.section.3) [Storing Responses in Caches](#response.cacheability)

A cache *MUST NOT* store a response to a request unless:[¶](#rfc.section.3.p.1)

- the request method is understood by the cache;
- the response status code is final (see [Section 15](rfc9110.html#status.codes "Status Codes") of [[HTTP]](#HTTP));
- if the response status code is 206 or 304, or the must-understand cache directive
  (see [Section 5.2.2.3](#cache-response-directive.must-understand "must-understand")) is present: the cache understands the response status code;
- the no-store cache directive is not present in the response (see [Section 5.2.2.5](#cache-response-directive.no-store "no-store"));
- if the cache is shared: the private response directive is either not present or allows
  a shared cache to store a modified response; see [Section 5.2.2.7](#cache-response-directive.private "private"));
- if the cache is shared: the [Authorization](rfc9110.html#field.authorization) header field is not present in the request (see [Section 11.6.2](rfc9110.html#field.authorization "Authorization") of [[HTTP]](#HTTP)) or a response directive is present that explicitly allows shared caching (see [Section 3.5](#caching.authenticated.responses "Storing Responses to Authenticated Requests")); and
- the response contains at least one of the following:

  - a public response directive (see [Section 5.2.2.9](#cache-response-directive.public "public"));
  - a private response directive, if the cache is not shared (see [Section 5.2.2.7](#cache-response-directive.private "private"));
  - an [Expires](#field.expires) header field (see [Section 5.3](#field.expires "Expires"));
  - a max-age response directive (see [Section 5.2.2.1](#cache-response-directive.max-age "max-age"));
  - if the cache is shared: an s-maxage response directive (see [Section 5.2.2.10](#cache-response-directive.s-maxage "s-maxage"));
  - a cache extension that allows it to be cached (see [Section 5.2.3](#cache.control.extensions "Extension Directives")); or
  - a status code that is defined as heuristically cacheable (see [Section 4.2.2](#heuristic.freshness "Calculating Heuristic Freshness")).

Note that a cache extension can override any of the requirements listed; see [Section 5.2.3](#cache.control.extensions "Extension Directives").[¶](#rfc.section.3.p.3)

In this context, a cache has "understood" a request method or a response status code
if it recognizes it and implements all specified caching-related behavior.[¶](#rfc.section.3.p.4)

Note that, in normal operation, some caches will not store a response that has neither
a cache validator nor an explicit expiration time, as such responses are not usually
useful to store. However, caches are not prohibited from storing such responses.[¶](#rfc.section.3.p.5)

### [3.1.](#rfc.section.3.1) [Storing Header and Trailer Fields](#storing.fields)

Caches *MUST* include all received response header fields — including unrecognized ones — when storing
a response; this assures that new HTTP header fields can be successfully deployed.
However, the following exceptions are made:[¶](#rfc.section.3.1.p.1)

- The Connection header field and fields whose names are listed in it are required by [Section 7.6.1](rfc9110.html#field.connection "Connection") of [[HTTP]](#HTTP) to be removed before forwarding the message. This *MAY* be implemented by doing so before storage.
- Likewise, some fields' semantics require them to be removed before forwarding the
  message, and this *MAY* be implemented by doing so before storage; see [Section 7.6.1](rfc9110.html#field.connection "Connection") of [[HTTP]](#HTTP) for some examples.
- The no-cache ([Section 5.2.2.4](#cache-response-directive.no-cache "no-cache")) and private ([Section 5.2.2.7](#cache-response-directive.private "private")) cache directives can have arguments that prevent storage of header fields by all
  caches and shared caches, respectively.
- Header fields that are specific to the proxy that a cache uses when forwarding a request *MUST NOT* be stored, unless the cache incorporates the identity of the proxy into the cache
  key. Effectively, this is limited to Proxy-Authenticate ([Section 11.7.1](rfc9110.html#field.proxy-authenticate "Proxy-Authenticate") of [[HTTP]](#HTTP)), Proxy-Authentication-Info ([Section 11.7.3](rfc9110.html#field.proxy-authentication-info "Proxy-Authentication-Info") of [[HTTP]](#HTTP)), and Proxy-Authorization ([Section 11.7.2](rfc9110.html#field.proxy-authorization "Proxy-Authorization") of [[HTTP]](#HTTP)).

Caches *MAY* either store trailer fields separate from header fields or discard them. Caches *MUST NOT* combine trailer fields with header fields.[¶](#rfc.section.3.1.p.3)

### [3.2.](#rfc.section.3.2) [Updating Stored Header Fields](#update)

Caches are required to update a stored response's header fields from another (typically
newer) response in several situations; for example, see Sections [3.4](#combining.responses "Combining Partial Content"), [4.3.4](#freshening.responses "Freshening Stored Responses upon Validation"), and [4.3.5](#head.effects "Freshening Responses with HEAD").[¶](#rfc.section.3.2.p.1)

When doing so, the cache *MUST* add each header field in the provided response to the stored response, replacing field
values that are already present, with the following exceptions:[¶](#rfc.section.3.2.p.2)

- Header fields excepted from storage in [Section 3.1](#storing.fields "Storing Header and Trailer Fields"),
- Header fields that the cache's stored response depends upon, as described below,
- Header fields that are automatically processed and removed by the recipient, as described
  below, and
- The [Content-Length](rfc9110.html#field.content-length) header field.

In some cases, caches (especially in user agents) store the results of processing
the received response, rather than the response itself, and updating header fields
that affect that processing can result in inconsistent behavior and security issues.
Caches in this situation *MAY* omit these header fields from updating stored responses on an exceptional basis but *SHOULD* limit such omission to those fields necessary to assure integrity of the stored response.[¶](#rfc.section.3.2.p.4)

For example, a browser might decode the content coding of a response while it is being
received, creating a disconnect between the data it has stored and the response's
original metadata. Updating that stored metadata with a different [Content-Encoding](rfc9110.html#field.content-encoding) header field would be problematic. Likewise, a browser might store a post-parse HTML
tree rather than the content received in the response; updating the [Content-Type](rfc9110.html#field.content-type) header field would not be workable in this case because any assumptions about the
format made in parsing would now be invalid.[¶](#rfc.section.3.2.p.5)

Furthermore, some fields are automatically processed and removed by the HTTP implementation,
such as the [Content-Range](rfc9110.html#field.content-range) header field. Implementations *MAY* automatically omit such header fields from updates, even when the processing does
not actually occur.[¶](#rfc.section.3.2.p.6)

Note that the Content-\* prefix is not a signal that a header field is omitted from
update; it is a convention for MIME header fields, not HTTP.[¶](#rfc.section.3.2.p.7)

### [3.3.](#rfc.section.3.3) [Storing Incomplete Responses](#incomplete.responses)

If the request method is GET, the response status code is [200
(OK)](rfc9110.html#status.200), and the entire response header section has been received, a cache *MAY* store a response that is not complete ([Section 6.1](rfc9110.html#message.framing "Framing and Completeness") of [[HTTP]](#HTTP)) provided that the stored response is recorded as being incomplete. Likewise, a [206 (Partial
Content)](rfc9110.html#status.206) response *MAY* be stored as if it were an incomplete [200 (OK)](rfc9110.html#status.200) response. However, a cache *MUST NOT* store incomplete or partial-content responses if it does not support the [Range](rfc9110.html#field.range) and [Content-Range](rfc9110.html#field.content-range) header fields or if it does not understand the range units used in those fields.[¶](#rfc.section.3.3.p.1)

A cache *MAY* complete a stored incomplete response by making a subsequent range request ([Section 14.2](rfc9110.html#field.range "Range") of [[HTTP]](#HTTP)) and combining the successful response with the stored response, as defined in [Section 3.4](#combining.responses "Combining Partial Content"). A cache *MUST NOT* use an incomplete response to answer requests unless the response has been made complete,
or the request is partial and specifies a range wholly within the incomplete response.
A cache *MUST NOT* send a partial response to a client without explicitly marking it using the [206 (Partial Content)](rfc9110.html#status.206) status code.[¶](#rfc.section.3.3.p.2)

### [3.4.](#rfc.section.3.4) [Combining Partial Content](#combining.responses)

A response might transfer only a partial representation if the connection closed prematurely
or if the request used one or more Range specifiers ([Section 14.2](rfc9110.html#field.range "Range") of [[HTTP]](#HTTP)). After several such transfers, a cache might have received several ranges of the
same representation. A cache *MAY* combine these ranges into a single stored response, and reuse that response to satisfy
later requests, if they all share the same strong validator and the cache complies
with the client requirements in [Section 15.3.7.3](rfc9110.html#combining.byte.ranges "Combining Parts") of [[HTTP]](#HTTP).[¶](#rfc.section.3.4.p.1)

When combining the new response with one or more stored responses, a cache *MUST* update the stored response header fields using the header fields provided in the new
response, as per [Section 3.2](#update "Updating Stored Header Fields").[¶](#rfc.section.3.4.p.2)

### [3.5.](#rfc.section.3.5) [Storing Responses to Authenticated Requests](#caching.authenticated.responses)

A shared cache *MUST NOT* use a cached response to a request with an [Authorization](rfc9110.html#field.authorization) header field ([Section 11.6.2](rfc9110.html#field.authorization "Authorization") of [[HTTP]](#HTTP)) to satisfy any subsequent request unless the response contains a [Cache-Control](#field.cache-control) field with a response directive ([Section 5.2.2](#cache-response-directive "Response Directives")) that allows it to be stored by a shared cache, and the cache conforms to the requirements
of that directive for that response.[¶](#rfc.section.3.5.p.1)

In this specification, the following response directives have such an effect: must-revalidate
([Section 5.2.2.2](#cache-response-directive.must-revalidate "must-revalidate")), public ([Section 5.2.2.9](#cache-response-directive.public "public")), and s-maxage ([Section 5.2.2.10](#cache-response-directive.s-maxage "s-maxage")).[¶](#rfc.section.3.5.p.2)

## [4.](#rfc.section.4) [Constructing Responses from Caches](#constructing.responses.from.caches)

When presented with a request, a cache *MUST NOT* reuse a stored response unless:[¶](#rfc.section.4.p.1)

- the presented target URI ([Section 7.1](rfc9110.html#target.resource "Determining the Target Resource") of [[HTTP]](#HTTP)) and that of the stored response match, and
- the request method associated with the stored response allows it to be used for the
  presented request, and
- request header fields nominated by the stored response (if any) match those presented
  (see [Section 4.1](#caching.negotiated.responses "Calculating Cache Keys with the Vary Header Field")), and
- the stored response does not contain the no-cache directive ([Section 5.2.2.4](#cache-response-directive.no-cache "no-cache")), unless it is successfully validated ([Section 4.3](#validation.model "Validation")), and
- the stored response is one of the following:

  - fresh (see [Section 4.2](#expiration.model "Freshness")), or
  - allowed to be served stale (see [Section 4.2.4](#serving.stale.responses "Serving Stale Responses")), or
  - successfully validated (see [Section 4.3](#validation.model "Validation")).

Note that a cache extension can override any of the requirements listed; see [Section 5.2.3](#cache.control.extensions "Extension Directives").[¶](#rfc.section.4.p.3)

When a stored response is used to satisfy a request without validation, a cache *MUST* generate an [Age](#field.age) header field ([Section 5.1](#field.age "Age")), replacing any present in the response with a value equal to the stored response's
current\_age; see [Section 4.2.3](#age.calculations "Calculating Age").[¶](#rfc.section.4.p.4)

A cache *MUST* write through requests with methods that are unsafe ([Section 9.2.1](rfc9110.html#safe.methods "Safe Methods") of [[HTTP]](#HTTP)) to the origin server; i.e., a cache is not allowed to generate a reply to such a
request before having forwarded the request and having received a corresponding response.[¶](#rfc.section.4.p.5)

Also, note that unsafe requests might invalidate already-stored responses; see [Section 4.4](#invalidation "Invalidating Stored Responses").[¶](#rfc.section.4.p.6)

A cache can use a response that is stored or storable to satisfy multiple requests,
provided that it is allowed to reuse that response for the requests in question. This
enables a cache to collapse requests — or combine multiple incoming requests into a single forward request upon a cache
miss — thereby reducing load on the origin server and network. Note, however, that
if the cache cannot use the returned response for some or all of the collapsed requests,
it will need to forward the requests in order to satisfy them, potentially introducing
additional latency.[¶](#rfc.section.4.p.7)

When more than one suitable response is stored, a cache *MUST* use the most recent one (as determined by the [Date](rfc9110.html#field.date) header field). It can also forward the request with "Cache-Control: max-age=0" or
"Cache-Control: no-cache" to disambiguate which response to use.[¶](#rfc.section.4.p.8)

A cache without a clock ([Section 5.6.7](rfc9110.html#http.date "Date/Time Formats") of [[HTTP]](#HTTP)) *MUST* revalidate stored responses upon every use.[¶](#rfc.section.4.p.9)

### [4.1.](#rfc.section.4.1) [Calculating Cache Keys with the Vary Header Field](#caching.negotiated.responses)

When a cache receives a request that can be satisfied by a stored response and that
stored response contains a [Vary](rfc9110.html#field.vary) header field ([Section 12.5.5](rfc9110.html#field.vary "Vary") of [[HTTP]](#HTTP)), the cache *MUST NOT* use that stored response without revalidation unless all the presented request header
fields nominated by that Vary field value match those fields in the original request
(i.e., the request that caused the cached response to be stored).[¶](#rfc.section.4.1.p.1)

The header fields from two requests are defined to match if and only if those in the
first request can be transformed to those in the second request by applying any of
the following:[¶](#rfc.section.4.1.p.2)

- adding or removing whitespace, where allowed in the header field's syntax
- combining multiple header field lines with the same field name (see [Section 5.2](rfc9110.html#field.lines "Field Lines and Combined Field Value") of [[HTTP]](#HTTP))
- normalizing both header field values in a way that is known to have identical semantics,
  according to the header field's specification (e.g., reordering field values when
  order is not significant; case-normalization, where values are defined to be case-insensitive)

If (after any normalization that might take place) a header field is absent from a
request, it can only match another request if it is also absent there.[¶](#rfc.section.4.1.p.4)

A stored response with a [Vary](rfc9110.html#field.vary) header field value containing a member "\*" always fails to match.[¶](#rfc.section.4.1.p.5)

If multiple stored responses match, the cache will need to choose one to use. When
a nominated request header field has a known mechanism for ranking preference (e.g.,
qvalues on [Accept](rfc9110.html#field.accept) and similar request header fields), that mechanism *MAY* be used to choose a preferred response. If such a mechanism is not available, or leads
to equally preferred responses, the most recent response (as determined by the [Date](rfc9110.html#field.date) header field) is chosen, as per [Section 4](#constructing.responses.from.caches "Constructing Responses from Caches").[¶](#rfc.section.4.1.p.6)

Some resources mistakenly omit the Vary header field from their default response (i.e.,
the one sent when the request does not express any preferences), with the effect of
choosing it for subsequent requests to that resource even when more preferable responses
are available. When a cache has multiple stored responses for a target URI and one
or more omits the Vary header field, the cache *SHOULD* choose the most recent (see [Section 4.2.3](#age.calculations "Calculating Age")) stored response with a valid Vary field value.[¶](#rfc.section.4.1.p.7)

If no stored response matches, the cache cannot satisfy the presented request. Typically,
the request is forwarded to the origin server, potentially with preconditions added
to describe what responses the cache has already stored ([Section 4.3](#validation.model "Validation")).[¶](#rfc.section.4.1.p.8)

### [4.2.](#rfc.section.4.2) [Freshness](#expiration.model)

A fresh response is one whose age has not yet exceeded its freshness lifetime. Conversely,
a stale response is one where it has.[¶](#rfc.section.4.2.p.1)

A response's freshness lifetime is the length of time between its generation by the origin server and its expiration
time. An explicit expiration time is the time at which the origin server intends that a stored response can no longer
be used by a cache without further validation, whereas a heuristic expiration time is assigned by a cache when no explicit expiration time is available.[¶](#rfc.section.4.2.p.2)

A response's age is the time that has passed since it was generated by, or successfully validated with,
the origin server.[¶](#rfc.section.4.2.p.3)

When a response is fresh, it can be used to satisfy subsequent requests without contacting
the origin server, thereby improving efficiency.[¶](#rfc.section.4.2.p.4)

The primary mechanism for determining freshness is for an origin server to provide
an explicit expiration time in the future, using either the [Expires](#field.expires) header field ([Section 5.3](#field.expires "Expires")) or the max-age response directive ([Section 5.2.2.1](#cache-response-directive.max-age "max-age")). Generally, origin servers will assign future explicit expiration times to responses
in the belief that the representation is not likely to change in a semantically significant
way before the expiration time is reached.[¶](#rfc.section.4.2.p.5)

If an origin server wishes to force a cache to validate every request, it can assign
an explicit expiration time in the past to indicate that the response is already stale.
Compliant caches will normally validate a stale cached response before reusing it
for subsequent requests (see [Section 4.2.4](#serving.stale.responses "Serving Stale Responses")).[¶](#rfc.section.4.2.p.6)

Since origin servers do not always provide explicit expiration times, caches are also
allowed to use a heuristic to determine an expiration time under certain circumstances
(see [Section 4.2.2](#heuristic.freshness "Calculating Heuristic Freshness")).[¶](#rfc.section.4.2.p.7)

The calculation to determine if a response is fresh is:[¶](#rfc.section.4.2.p.8)

```
   response_is_fresh = (freshness_lifetime > current_age)
```

freshness\_lifetime is defined in [Section 4.2.1](#calculating.freshness.lifetime "Calculating Freshness Lifetime"); current\_age is defined in [Section 4.2.3](#age.calculations "Calculating Age").[¶](#rfc.section.4.2.p.10)

Clients can send the max-age or min-fresh request directives ([Section 5.2.1](#cache-request-directive "Request Directives")) to suggest limits on the freshness calculations for the corresponding response.
However, caches are not required to honor them.[¶](#rfc.section.4.2.p.11)

When calculating freshness, to avoid common problems in date parsing:[¶](#rfc.section.4.2.p.12)

- Although all date formats are specified to be case-sensitive, a cache recipient *SHOULD* match the field value case-insensitively.
- If a cache recipient's internal implementation of time has less resolution than the
  value of an HTTP-date, the recipient *MUST* internally represent a parsed [Expires](#field.expires) date as the nearest time equal to or earlier than the received value.
- A cache recipient *MUST NOT* allow local time zones to influence the calculation or comparison of an age or expiration
  time.
- A cache recipient *SHOULD* consider a date with a zone abbreviation other than "GMT" to be invalid for calculating
  expiration.

Note that freshness applies only to cache operation; it cannot be used to force a
user agent to refresh its display or reload a resource. See [Section 6](#history.lists "Relationship to Applications and Other Caches") for an explanation of the difference between caches and history mechanisms.[¶](#rfc.section.4.2.p.14)

#### [4.2.1.](#rfc.section.4.2.1) [Calculating Freshness Lifetime](#calculating.freshness.lifetime)

A cache can calculate the freshness lifetime (denoted as freshness\_lifetime) of a
response by evaluating the following rules and using the first match:[¶](#rfc.section.4.2.1.p.1)

- If the cache is shared and the s-maxage response directive ([Section 5.2.2.10](#cache-response-directive.s-maxage "s-maxage")) is present, use its value, or
- If the max-age response directive ([Section 5.2.2.1](#cache-response-directive.max-age "max-age")) is present, use its value, or
- If the [Expires](#field.expires) response header field ([Section 5.3](#field.expires "Expires")) is present, use its value minus the value of the [Date](rfc9110.html#field.date) response header field (using the time the message was received if it is not present,
  as per [Section 6.6.1](rfc9110.html#field.date "Date") of [[HTTP]](#HTTP)), or
- Otherwise, no explicit expiration time is present in the response. A heuristic freshness
  lifetime might be applicable; see [Section 4.2.2](#heuristic.freshness "Calculating Heuristic Freshness").

Note that this calculation is intended to reduce clock skew by using the clock information
provided by the origin server whenever possible.[¶](#rfc.section.4.2.1.p.3)

When there is more than one value present for a given directive (e.g., two [Expires](#field.expires) header field lines or multiple Cache-Control: max-age directives), either the first
occurrence should be used or the response should be considered stale. If directives
conflict (e.g., both max-age and no-cache are present), the most restrictive directive
should be honored. Caches are encouraged to consider responses that have invalid freshness
information (e.g., a max-age directive with non-integer content) to be stale.[¶](#rfc.section.4.2.1.p.4)

#### [4.2.2.](#rfc.section.4.2.2) [Calculating Heuristic Freshness](#heuristic.freshness)

Since origin servers do not always provide explicit expiration times, a cache *MAY* assign a heuristic expiration time when an explicit time is not specified, employing
algorithms that use other field values (such as the [Last-Modified](rfc9110.html#field.last-modified) time) to estimate a plausible expiration time. This specification does not provide
specific algorithms, but it does impose worst-case constraints on their results.[¶](#rfc.section.4.2.2.p.1)

A cache *MUST NOT* use heuristics to determine freshness when an explicit expiration time is present
in the stored response. Because of the requirements in [Section 3](#response.cacheability "Storing Responses in Caches"), heuristics can only be used on responses without explicit freshness whose status
codes are defined as heuristically cacheable (e.g., see [Section 15.1](rfc9110.html#overview.of.status.codes "Overview of Status Codes") of [[HTTP]](#HTTP)) and on responses without explicit freshness that have been marked as explicitly
cacheable (e.g., with a public response directive).[¶](#rfc.section.4.2.2.p.2)

Note that in previous specifications, heuristically cacheable response status codes
were called "cacheable by default".[¶](#rfc.section.4.2.2.p.3)

If the response has a [Last-Modified](rfc9110.html#field.last-modified) header field ([Section 8.8.2](rfc9110.html#field.last-modified "Last-Modified") of [[HTTP]](#HTTP)), caches are encouraged to use a heuristic expiration value that is no more than
some fraction of the interval since that time. A typical setting of this fraction
might be 10%.[¶](#rfc.section.4.2.2.p.4)

**Note:** A previous version of the HTTP specification ([Section 13.9](https://www.rfc-editor.org/rfc/rfc2616.html#section-13.9) of [[RFC2616]](#RFC2616)) prohibited caches from calculating heuristic freshness for URIs with query components
(i.e., those containing "?"). In practice, this has not been widely implemented. Therefore,
origin servers are encouraged to send explicit directives (e.g., Cache-Control: no-cache)
if they wish to prevent caching.[¶](#rfc.section.4.2.2.p.5.1)

#### [4.2.3.](#rfc.section.4.2.3) [Calculating Age](#age.calculations)

The [Age](#field.age) header field is used to convey an estimated age of the response message when obtained
from a cache. The Age field value is the cache's estimate of the number of seconds
since the origin server generated or validated the response. The Age value is therefore
the sum of the time that the response has been resident in each of the caches along
the path from the origin server, plus the time it has been in transit along network
paths.[¶](#rfc.section.4.2.3.p.1)

Age calculation uses the following data:[¶](#rfc.section.4.2.3.p.2)

age\_value
:   The term "age\_value" denotes the value of the [Age](#field.age) header field ([Section 5.1](#field.age "Age")), in a form appropriate for arithmetic operation; or 0, if not available.

date\_value
:   The term "date\_value" denotes the value of the Date header field, in a form appropriate
    for arithmetic operations. See [Section 6.6.1](rfc9110.html#field.date "Date") of [[HTTP]](#HTTP) for the definition of the Date header field and for requirements regarding responses
    without it.

now
:   The term "now" means the current value of this implementation's clock ([Section 5.6.7](rfc9110.html#http.date "Date/Time Formats") of [[HTTP]](#HTTP)).

request\_time
:   The value of the clock at the time of the request that resulted in the stored response.

response\_time
:   The value of the clock at the time the response was received.

A response's age can be calculated in two entirely independent ways:[¶](#rfc.section.4.2.3.p.4)

1. the "apparent\_age": response\_time minus date\_value, if the implementation's clock
   is reasonably well synchronized to the origin server's clock. If the result is negative,
   the result is replaced by zero.
2. the "corrected\_age\_value", if all of the caches along the response path implement
   HTTP/1.1 or greater. A cache *MUST* interpret this value relative to the time the request was initiated, not the time
   that the response was received.

```
  apparent_age = max(0, response_time - date_value);

  response_delay = response_time - request_time;
  corrected_age_value = age_value + response_delay;
```

The corrected\_age\_value *MAY* be used as the corrected\_initial\_age. In circumstances where very old cache implementations
that might not correctly insert [Age](#field.age) are present, corrected\_initial\_age can be calculated more conservatively as[¶](#rfc.section.4.2.3.p.7)

```
  corrected_initial_age = max(apparent_age, corrected_age_value);
```

The current\_age of a stored response can then be calculated by adding the time (in
seconds) since the stored response was last validated by the origin server to the
corrected\_initial\_age.[¶](#rfc.section.4.2.3.p.9)

```
  resident_time = now - response_time;
  current_age = corrected_initial_age + resident_time;
```

#### [4.2.4.](#rfc.section.4.2.4) [Serving Stale Responses](#serving.stale.responses)

A "stale" response is one that either has explicit expiry information or is allowed
to have heuristic expiry calculated, but is not fresh according to the calculations
in [Section 4.2](#expiration.model "Freshness").[¶](#rfc.section.4.2.4.p.1)

A cache *MUST NOT* generate a stale response if it is prohibited by an explicit in-protocol directive
(e.g., by a no-cache response directive, a must-revalidate response directive, or
an applicable s-maxage or proxy-revalidate response directive; see [Section 5.2.2](#cache-response-directive "Response Directives")).[¶](#rfc.section.4.2.4.p.2)

A cache *MUST NOT* generate a stale response unless it is disconnected or doing so is explicitly permitted
by the client or origin server (e.g., by the max-stale request directive in [Section 5.2.1](#cache-request-directive "Request Directives"), extension directives such as those defined in [[RFC5861]](#RFC5861), or configuration in accordance with an out-of-band contract).[¶](#rfc.section.4.2.4.p.3)

### [4.3.](#rfc.section.4.3) [Validation](#validation.model)

When a cache has one or more stored responses for a requested URI, but cannot serve
any of them (e.g., because they are not fresh, or one cannot be chosen; see [Section 4.1](#caching.negotiated.responses "Calculating Cache Keys with the Vary Header Field")), it can use the conditional request mechanism ([Section 13](rfc9110.html#conditional.requests "Conditional Requests") of [[HTTP]](#HTTP)) in the forwarded request to give the next inbound server an opportunity to choose
a valid stored response to use, updating the stored metadata in the process, or to
replace the stored response(s) with a new response. This process is known as validating or revalidating the stored response.[¶](#rfc.section.4.3.p.1)

#### [4.3.1.](#rfc.section.4.3.1) [Sending a Validation Request](#validation.sent)

When generating a conditional request for validation, a cache either starts with a
request it is attempting to satisfy or — if it is initiating the request independently
— synthesizes a request using a stored response by copying the method, target URI,
and request header fields identified by the Vary header field ([Section 4.1](#caching.negotiated.responses "Calculating Cache Keys with the Vary Header Field")).[¶](#rfc.section.4.3.1.p.1)

It then updates that request with one or more precondition header fields. These contain
validator metadata sourced from a stored response(s) that has the same URI. Typically,
this will include only the stored response(s) that has the same cache key, although
a cache is allowed to validate a response that it cannot choose with the request header
fields it is sending (see [Section 4.1](#caching.negotiated.responses "Calculating Cache Keys with the Vary Header Field")).[¶](#rfc.section.4.3.1.p.2)

The precondition header fields are then compared by recipients to determine whether
any stored response is equivalent to a current representation of the resource.[¶](#rfc.section.4.3.1.p.3)

One such validator is the timestamp given in a [Last-Modified](rfc9110.html#field.last-modified) header field ([Section 8.8.2](rfc9110.html#field.last-modified "Last-Modified") of [[HTTP]](#HTTP)), which can be used in an [If-Modified-Since](rfc9110.html#field.if-modified-since) header field for response validation, or in an [If-Unmodified-Since](rfc9110.html#field.if-unmodified-since) or [If-Range](rfc9110.html#field.if-range) header field for representation selection (i.e., the client is referring specifically
to a previously obtained representation with that timestamp).[¶](#rfc.section.4.3.1.p.4)

Another validator is the entity tag given in an [ETag](rfc9110.html#field.etag) field ([Section 8.8.3](rfc9110.html#field.etag "ETag") of [[HTTP]](#HTTP)). One or more entity tags, indicating one or more stored responses, can be used in
an [If-None-Match](rfc9110.html#field.if-none-match) header field for response validation, or in an [If-Match](rfc9110.html#field.if-match) or [If-Range](rfc9110.html#field.if-range) header field for representation selection (i.e., the client is referring specifically
to one or more previously obtained representations with the listed entity tags).[¶](#rfc.section.4.3.1.p.5)

When generating a conditional request for validation, a cache:[¶](#rfc.section.4.3.1.p.6)

- *MUST* send the relevant entity tags (using [If-Match](rfc9110.html#field.if-match), [If-None-Match](rfc9110.html#field.if-none-match), or [If-Range](rfc9110.html#field.if-range)) if the entity tags were provided in the stored response(s) being validated.
- *SHOULD* send the [Last-Modified](rfc9110.html#field.last-modified) value (using [If-Modified-Since](rfc9110.html#field.if-modified-since)) if the request is not for a subrange, a single stored response is being validated,
  and that response contains a Last-Modified value.
- *MAY* send the [Last-Modified](rfc9110.html#field.last-modified) value (using [If-Unmodified-Since](rfc9110.html#field.if-unmodified-since) or [If-Range](rfc9110.html#field.if-range)) if the request is for a subrange, a single stored response is being validated, and
  that response contains only a Last-Modified value (not an entity tag).

In most cases, both validators are generated in cache validation requests, even when
entity tags are clearly superior, to allow old intermediaries that do not understand
entity tag preconditions to respond appropriately.[¶](#rfc.section.4.3.1.p.8)

#### [4.3.2.](#rfc.section.4.3.2) [Handling a Received Validation Request](#validation.received)

Each client in the request chain may have its own cache, so it is common for a cache
at an intermediary to receive conditional requests from other (outbound) caches. Likewise,
some user agents make use of conditional requests to limit data transfers to recently
modified representations or to complete the transfer of a partially retrieved representation.[¶](#rfc.section.4.3.2.p.1)

If a cache receives a request that can be satisfied by reusing a stored [200 (OK)](rfc9110.html#status.200) or [206 (Partial Content)](rfc9110.html#status.206) response, as per [Section 4](#constructing.responses.from.caches "Constructing Responses from Caches"), the cache *SHOULD* evaluate any applicable conditional header field preconditions received in that request
with respect to the corresponding validators contained within the stored response.[¶](#rfc.section.4.3.2.p.2)

A cache *MUST NOT* evaluate conditional header fields that only apply to an origin server, occur in a
request with semantics that cannot be satisfied with a cached response, or occur in
a request with a target resource for which it has no stored responses; such preconditions
are likely intended for some other (inbound) server.[¶](#rfc.section.4.3.2.p.3)

The proper evaluation of conditional requests by a cache depends on the received precondition
header fields and their precedence. In summary, the [If-Match](rfc9110.html#field.if-match) and [If-Unmodified-Since](rfc9110.html#field.if-unmodified-since) conditional header fields are not applicable to a cache, and [If-None-Match](rfc9110.html#field.if-none-match) takes precedence over [If-Modified-Since](rfc9110.html#field.if-modified-since). See [Section 13.2.2](rfc9110.html#precedence "Precedence of Preconditions") of [[HTTP]](#HTTP) for a complete specification of precondition precedence.[¶](#rfc.section.4.3.2.p.4)

A request containing an [If-None-Match](rfc9110.html#field.if-none-match) header field ([Section 13.1.2](rfc9110.html#field.if-none-match "If-None-Match") of [[HTTP]](#HTTP)) indicates that the client wants to validate one or more of its own stored responses
in comparison to the stored response chosen by the cache (as per [Section 4](#constructing.responses.from.caches "Constructing Responses from Caches")).[¶](#rfc.section.4.3.2.p.5)

If an [If-None-Match](rfc9110.html#field.if-none-match) header field is not present, a request containing an [If-Modified-Since](rfc9110.html#field.if-modified-since) header field ([Section 13.1.3](rfc9110.html#field.if-modified-since "If-Modified-Since") of [[HTTP]](#HTTP)) indicates that the client wants to validate one or more of its own stored responses
by modification date.[¶](#rfc.section.4.3.2.p.6)

If a request contains an [If-Modified-Since](rfc9110.html#field.if-modified-since) header field and the [Last-Modified](rfc9110.html#field.last-modified) header field is not present in a stored response, a cache *SHOULD* use the stored response's [Date](rfc9110.html#field.date) field value (or, if no Date field is present, the time that the stored response was
received) to evaluate the conditional.[¶](#rfc.section.4.3.2.p.7)

A cache that implements partial responses to range requests, as defined in [Section 14.2](rfc9110.html#field.range "Range") of [[HTTP]](#HTTP), also needs to evaluate a received [If-Range](rfc9110.html#field.if-range) header field ([Section 13.1.5](rfc9110.html#field.if-range "If-Range") of [[HTTP]](#HTTP)) with respect to the cache's chosen response.[¶](#rfc.section.4.3.2.p.8)

When a cache decides to forward a request to revalidate its own stored responses for
a request that contains an [If-None-Match](rfc9110.html#field.if-none-match) list of entity tags, the cache *MAY* combine the received list with a list of entity tags from its own stored set of responses
(fresh or stale) and send the union of the two lists as a replacement [If-None-Match](rfc9110.html#field.if-none-match) header field value in the forwarded request. If a stored response contains only partial
content, the cache *MUST NOT* include its entity tag in the union unless the request is for a range that would be
fully satisfied by that partial stored response. If the response to the forwarded
request is [304 (Not Modified)](rfc9110.html#status.304) and has an ETag field value with an entity tag that is not in the client's list, the
cache *MUST* generate a [200 (OK)](rfc9110.html#status.200) response for the client by reusing its corresponding stored response, as updated by
the 304 response metadata ([Section 4.3.4](#freshening.responses "Freshening Stored Responses upon Validation")).[¶](#rfc.section.4.3.2.p.9)

#### [4.3.3.](#rfc.section.4.3.3) [Handling a Validation Response](#validation.response)

Cache handling of a response to a conditional request depends upon its status code:[¶](#rfc.section.4.3.3.p.1)

- A [304 (Not Modified)](rfc9110.html#status.304) response status code indicates that the stored response can be updated and reused;
  see [Section 4.3.4](#freshening.responses "Freshening Stored Responses upon Validation").
- A full response (i.e., one containing content) indicates that none of the stored responses
  nominated in the conditional request are suitable. Instead, the cache *MUST* use the full response to satisfy the request. The cache *MAY* store such a full response, subject to its constraints (see [Section 3](#response.cacheability "Storing Responses in Caches")).
- However, if a cache receives a [5xx (Server Error)](rfc9110.html#status.5xx) response while attempting to validate a response, it can either forward this response
  to the requesting client or act as if the server failed to respond. In the latter
  case, the cache can send a previously stored response, subject to its constraints
  on doing so (see [Section 4.2.4](#serving.stale.responses "Serving Stale Responses")), or retry the validation request.

#### [4.3.4.](#rfc.section.4.3.4) [Freshening Stored Responses upon Validation](#freshening.responses)

When a cache receives a [304 (Not Modified)](rfc9110.html#status.304) response, it needs to identify stored responses that are suitable for updating with
the new information provided, and then do so.[¶](#rfc.section.4.3.4.p.1)

The initial set of stored responses to update are those that could have been chosen
for that request — i.e., those that meet the requirements in [Section 4](#constructing.responses.from.caches "Constructing Responses from Caches"), except the last requirement to be fresh, able to be served stale, or just validated.[¶](#rfc.section.4.3.4.p.2)

Then, that initial set of stored responses is further filtered by the first match
of:[¶](#rfc.section.4.3.4.p.3)

- If the new response contains one or more strong validators (see [Section 8.8.1](rfc9110.html#weak.and.strong.validators "Weak versus Strong") of [[HTTP]](#HTTP)), then each of those strong validators identifies a selected representation for update.
  All the stored responses in the initial set with one of those same strong validators
  are identified for update. If none of the initial set contains at least one of the
  same strong validators, then the cache *MUST NOT* use the new response to update any stored responses.
- If the new response contains no strong validators but does contain one or more weak validators, and those validators correspond to one of the initial set's stored responses, then
  the most recent of those matching stored responses is identified for update.
- If the new response does not include any form of validator (such as where a client
  generates an [If-Modified-Since](rfc9110.html#field.if-modified-since) request from a source other than the [Last-Modified](rfc9110.html#field.last-modified) response header field), and there is only one stored response in the initial set,
  and that stored response also lacks a validator, then that stored response is identified
  for update.

For each stored response identified, the cache *MUST* update its header fields with the header fields provided in the [304 (Not
Modified)](rfc9110.html#status.304) response, as per [Section 3.2](#update "Updating Stored Header Fields").[¶](#rfc.section.4.3.4.p.5)

#### [4.3.5.](#rfc.section.4.3.5) [Freshening Responses with HEAD](#head.effects)

A response to the HEAD method is identical to what an equivalent request made with
a GET would have been, without sending the content. This property of HEAD responses
can be used to invalidate or update a cached GET response if the more efficient conditional
GET request mechanism is not available (due to no validators being present in the
stored response) or if transmission of the content is not desired even if it has changed.[¶](#rfc.section.4.3.5.p.1)

When a cache makes an inbound HEAD request for a target URI and receives a [200 (OK)](rfc9110.html#status.200) response, the cache *SHOULD* update or invalidate each of its stored GET responses that could have been chosen
for that request (see [Section 4.1](#caching.negotiated.responses "Calculating Cache Keys with the Vary Header Field")).[¶](#rfc.section.4.3.5.p.2)

For each of the stored responses that could have been chosen, if the stored response
and HEAD response have matching values for any received validator fields ([ETag](rfc9110.html#field.etag) and [Last-Modified](rfc9110.html#field.last-modified)) and, if the HEAD response has a [Content-Length](rfc9110.html#field.content-length) header field, the value of [Content-Length](rfc9110.html#field.content-length) matches that of the stored response, the cache *SHOULD* update the stored response as described below; otherwise, the cache *SHOULD* consider the stored response to be stale.[¶](#rfc.section.4.3.5.p.3)

If a cache updates a stored response with the metadata provided in a HEAD response,
the cache *MUST* use the header fields provided in the HEAD response to update the stored response
(see [Section 3.2](#update "Updating Stored Header Fields")).[¶](#rfc.section.4.3.5.p.4)

### [4.4.](#rfc.section.4.4) [Invalidating Stored Responses](#invalidation)

Because unsafe request methods ([Section 9.2.1](rfc9110.html#safe.methods "Safe Methods") of [[HTTP]](#HTTP)) such as PUT, POST, or DELETE have the potential for changing state on the origin
server, intervening caches are required to invalidate stored responses to keep their
contents up to date.[¶](#rfc.section.4.4.p.1)

A cache *MUST* invalidate the target URI ([Section 7.1](rfc9110.html#target.resource "Determining the Target Resource") of [[HTTP]](#HTTP)) when it receives a non-error status code in response to an unsafe request method
(including methods whose safety is unknown).[¶](#rfc.section.4.4.p.2)

A cache *MAY* invalidate other URIs when it receives a non-error status code in response to an unsafe
request method (including methods whose safety is unknown). In particular, the URI(s)
in the [Location](rfc9110.html#field.location) and [Content-Location](rfc9110.html#field.content-location) response header fields (if present) are candidates for invalidation; other URIs might
be discovered through mechanisms not specified in this document. However, a cache *MUST NOT* trigger an invalidation under these conditions if the origin ([Section 4.3.1](rfc9110.html#origin "URI Origin") of [[HTTP]](#HTTP)) of the URI to be invalidated differs from that of the target URI ([Section 7.1](rfc9110.html#target.resource "Determining the Target Resource") of [[HTTP]](#HTTP)). This helps prevent denial-of-service attacks.[¶](#rfc.section.4.4.p.3)

Invalidate means that the cache will either remove all stored responses whose target URI matches
the given URI or mark them as "invalid" and in need of a mandatory validation before
they can be sent in response to a subsequent request.[¶](#rfc.section.4.4.p.4)

A "non-error response" is one with a [2xx (Successful)](rfc9110.html#status.2xx) or [3xx (Redirection)](rfc9110.html#status.3xx) status code.[¶](#rfc.section.4.4.p.5)

Note that this does not guarantee that all appropriate responses are invalidated globally;
a state-changing request would only invalidate responses in the caches it travels
through.[¶](#rfc.section.4.4.p.6)

## [5.](#rfc.section.5) [Field Definitions](#header.field.definitions)

This section defines the syntax and semantics of HTTP fields related to caching.[¶](#rfc.section.5.p.1)

### [5.1.](#rfc.section.5.1) [Age](#field.age)

The "Age" response header field conveys the sender's estimate of the time since the
response was generated or successfully validated at the origin server. Age values
are calculated as specified in [Section 4.2.3](#age.calculations "Calculating Age").[¶](#rfc.section.5.1.p.1)

```
  Age = delta-seconds
```

The Age field value is a non-negative integer, representing time in seconds (see [Section 1.2.2](#delta-seconds "Delta Seconds")).[¶](#rfc.section.5.1.p.3)

Although it is defined as a singleton header field, a cache encountering a message
with a list-based Age field value *SHOULD* use the first member of the field value, discarding subsequent ones.[¶](#rfc.section.5.1.p.4)

If the field value (after discarding additional members, as per above) is invalid
(e.g., it contains something other than a non-negative integer), a cache *SHOULD* ignore the field.[¶](#rfc.section.5.1.p.5)

The presence of an Age header field implies that the response was not generated or
validated by the origin server for this request. However, lack of an Age header field
does not imply the origin was contacted.[¶](#rfc.section.5.1.p.6)

### [5.2.](#rfc.section.5.2) [Cache-Control](#field.cache-control)

The "Cache-Control" header field is used to list directives for caches along the request/response
chain. Cache directives are unidirectional, in that the presence of a directive in
a request does not imply that the same directive is present or copied in the response.[¶](#rfc.section.5.2.p.1)

See [Section 5.2.3](#cache.control.extensions "Extension Directives") for information about how Cache-Control directives defined elsewhere are handled.[¶](#rfc.section.5.2.p.2)

A proxy, whether or not it implements a cache, *MUST* pass cache directives through in forwarded messages, regardless of their significance
to that application, since the directives might apply to all recipients along the
request/response chain. It is not possible to target a directive to a specific cache.[¶](#rfc.section.5.2.p.3)

Cache directives are identified by a token, to be compared case-insensitively, and
have an optional argument that can use both token and quoted-string syntax. For the
directives defined below that define arguments, recipients ought to accept both forms,
even if a specific form is required for generation.[¶](#rfc.section.5.2.p.4)

```
  Cache-Control   = #cache-directive

  cache-directive = token [ "=" ( token / quoted-string ) ]
```

For the cache directives defined below, no argument is defined (nor allowed) unless
stated otherwise.[¶](#rfc.section.5.2.p.6)

#### [5.2.1.](#rfc.section.5.2.1) [Request Directives](#cache-request-directive)

This section defines cache request directives. They are advisory; caches *MAY* implement them, but are not required to.[¶](#rfc.section.5.2.1.p.1)

##### [5.2.1.1.](#rfc.section.5.2.1.1) [max-age](#cache-request-directive.max-age)

Argument syntax:[¶](#rfc.section.5.2.1.1.p.1)

- [delta-seconds](#delta-seconds) (see [Section 1.2.2](#delta-seconds "Delta Seconds"))

The max-age request directive indicates that the client prefers a response whose age
is less than or equal to the specified number of seconds. Unless the max-stale request
directive is also present, the client does not wish to receive a stale response.[¶](#rfc.section.5.2.1.1.p.3)

This directive uses the token form of the argument syntax: e.g., 'max-age=5' not 'max-age="5"'.
A sender *MUST NOT* generate the quoted-string form.[¶](#rfc.section.5.2.1.1.p.4)

##### [5.2.1.2.](#rfc.section.5.2.1.2) [max-stale](#cache-request-directive.max-stale)

Argument syntax:[¶](#rfc.section.5.2.1.2.p.1)

- [delta-seconds](#delta-seconds) (see [Section 1.2.2](#delta-seconds "Delta Seconds"))

The max-stale request directive indicates that the client will accept a response that
has exceeded its freshness lifetime. If a value is present, then the client is willing
to accept a response that has exceeded its freshness lifetime by no more than the
specified number of seconds. If no value is assigned to max-stale, then the client
will accept a stale response of any age.[¶](#rfc.section.5.2.1.2.p.3)

This directive uses the token form of the argument syntax: e.g., 'max-stale=10' not
'max-stale="10"'. A sender *MUST NOT* generate the quoted-string form.[¶](#rfc.section.5.2.1.2.p.4)

##### [5.2.1.3.](#rfc.section.5.2.1.3) [min-fresh](#cache-request-directive.min-fresh)

Argument syntax:[¶](#rfc.section.5.2.1.3.p.1)

- [delta-seconds](#delta-seconds) (see [Section 1.2.2](#delta-seconds "Delta Seconds"))

The min-fresh request directive indicates that the client prefers a response whose
freshness lifetime is no less than its current age plus the specified time in seconds.
That is, the client wants a response that will still be fresh for at least the specified
number of seconds.[¶](#rfc.section.5.2.1.3.p.3)

This directive uses the token form of the argument syntax: e.g., 'min-fresh=20' not
'min-fresh="20"'. A sender *MUST NOT* generate the quoted-string form.[¶](#rfc.section.5.2.1.3.p.4)

##### [5.2.1.4.](#rfc.section.5.2.1.4) [no-cache](#cache-request-directive.no-cache)

The no-cache request directive indicates that the client prefers a stored response
not be used to satisfy the request without successful validation on the origin server.[¶](#rfc.section.5.2.1.4.p.1)

##### [5.2.1.5.](#rfc.section.5.2.1.5) [no-store](#cache-request-directive.no-store)

The no-store request directive indicates that a cache *MUST NOT* store any part of either this request or any response to it. This directive applies
to both private and shared caches. "MUST NOT store" in this context means that the
cache *MUST NOT* intentionally store the information in non-volatile storage and *MUST* make a best-effort attempt to remove the information from volatile storage as promptly
as possible after forwarding it.[¶](#rfc.section.5.2.1.5.p.1)

This directive is not a reliable or sufficient mechanism for ensuring privacy. In
particular, malicious or compromised caches might not recognize or obey this directive,
and communications networks might be vulnerable to eavesdropping.[¶](#rfc.section.5.2.1.5.p.2)

Note that if a request containing this directive is satisfied from a cache, the no-store
request directive does not apply to the already stored response.[¶](#rfc.section.5.2.1.5.p.3)

##### [5.2.1.6.](#rfc.section.5.2.1.6) [no-transform](#cache-request-directive.no-transform)

The no-transform request directive indicates that the client is asking for intermediaries
to avoid transforming the content, as defined in [Section 7.7](rfc9110.html#message.transformations "Message Transformations") of [[HTTP]](#HTTP).[¶](#rfc.section.5.2.1.6.p.1)

##### [5.2.1.7.](#rfc.section.5.2.1.7) [only-if-cached](#cache-request-directive.only-if-cached)

The only-if-cached request directive indicates that the client only wishes to obtain
a stored response. Caches that honor this request directive *SHOULD*, upon receiving it, respond with either a stored response consistent with the other
constraints of the request or a [504 (Gateway Timeout)](rfc9110.html#status.504) status code.[¶](#rfc.section.5.2.1.7.p.1)

#### [5.2.2.](#rfc.section.5.2.2) [Response Directives](#cache-response-directive)

This section defines cache response directives. A cache *MUST* obey the Cache-Control directives defined in this section.[¶](#rfc.section.5.2.2.p.1)

##### [5.2.2.1.](#rfc.section.5.2.2.1) [max-age](#cache-response-directive.max-age)

Argument syntax:[¶](#rfc.section.5.2.2.1.p.1)

- [delta-seconds](#delta-seconds) (see [Section 1.2.2](#delta-seconds "Delta Seconds"))

The max-age response directive indicates that the response is to be considered stale
after its age is greater than the specified number of seconds.[¶](#rfc.section.5.2.2.1.p.3)

This directive uses the token form of the argument syntax: e.g., 'max-age=5' not 'max-age="5"'.
A sender *MUST NOT* generate the quoted-string form.[¶](#rfc.section.5.2.2.1.p.4)

##### [5.2.2.2.](#rfc.section.5.2.2.2) [must-revalidate](#cache-response-directive.must-revalidate)

The must-revalidate response directive indicates that once the response has become
stale, a cache *MUST NOT* reuse that response to satisfy another request until it has been successfully validated
by the origin, as defined by [Section 4.3](#validation.model "Validation").[¶](#rfc.section.5.2.2.2.p.1)

The must-revalidate directive is necessary to support reliable operation for certain
protocol features. In all circumstances, a cache *MUST NOT* ignore the must-revalidate directive; in particular, if a cache is disconnected, the
cache *MUST* generate an error response rather than reuse the stale response. The generated status
code *SHOULD* be [504 (Gateway Timeout)](rfc9110.html#status.504) unless another error status code is more applicable.[¶](#rfc.section.5.2.2.2.p.2)

The must-revalidate directive ought to be used by servers if and only if failure to
validate a request could cause incorrect operation, such as a silently unexecuted
financial transaction.[¶](#rfc.section.5.2.2.2.p.3)

The must-revalidate directive also permits a shared cache to reuse a response to a
request containing an [Authorization](rfc9110.html#field.authorization) header field ([Section 11.6.2](rfc9110.html#field.authorization "Authorization") of [[HTTP]](#HTTP)), subject to the above requirement on revalidation ([Section 3.5](#caching.authenticated.responses "Storing Responses to Authenticated Requests")).[¶](#rfc.section.5.2.2.2.p.4)

##### [5.2.2.3.](#rfc.section.5.2.2.3) [must-understand](#cache-response-directive.must-understand)

The must-understand response directive limits caching of the response to a cache that
understands and conforms to the requirements for that response's status code.[¶](#rfc.section.5.2.2.3.p.1)

A response that contains the must-understand directive *SHOULD* also contain the no-store directive. When a cache that implements the must-understand
directive receives a response that includes it, the cache *SHOULD* ignore the no-store directive if it understands and implements the status code's caching
requirements.[¶](#rfc.section.5.2.2.3.p.2)

##### [5.2.2.4.](#rfc.section.5.2.2.4) [no-cache](#cache-response-directive.no-cache)

Argument syntax:[¶](#rfc.section.5.2.2.4.p.1)

- #[field-name](#imported.rules)

The no-cache response directive, in its unqualified form (without an argument), indicates
that the response *MUST NOT* be used to satisfy any other request without forwarding it for validation and receiving
a successful response; see [Section 4.3](#validation.model "Validation").[¶](#rfc.section.5.2.2.4.p.3)

This allows an origin server to prevent a cache from using the response to satisfy
a request without contacting it, even by caches that have been configured to send
stale responses.[¶](#rfc.section.5.2.2.4.p.4)

The qualified form of the no-cache response directive, with an argument that lists
one or more field names, indicates that a cache *MAY* use the response to satisfy a subsequent request, subject to any other restrictions
on caching, if the listed header fields are excluded from the subsequent response
or the subsequent response has been successfully revalidated with the origin server
(updating or removing those fields). This allows an origin server to prevent the reuse
of certain header fields in a response, while still allowing caching of the rest of
the response.[¶](#rfc.section.5.2.2.4.p.5)

The field names given are not limited to the set of header fields defined by this
specification. Field names are case-insensitive.[¶](#rfc.section.5.2.2.4.p.6)

This directive uses the quoted-string form of the argument syntax. A sender *SHOULD NOT* generate the token form (even if quoting appears not to be needed for single-entry
lists).[¶](#rfc.section.5.2.2.4.p.7)

**Note:** The qualified form of the directive is often handled by caches as if an unqualified
no-cache directive was received; that is, the special handling for the qualified form
is not widely implemented.[¶](#rfc.section.5.2.2.4.p.8.1)

##### [5.2.2.5.](#rfc.section.5.2.2.5) [no-store](#cache-response-directive.no-store)

The no-store response directive indicates that a cache *MUST NOT* store any part of either the immediate request or the response and *MUST NOT* use the response to satisfy any other request.[¶](#rfc.section.5.2.2.5.p.1)

This directive applies to both private and shared caches. "MUST NOT store" in this
context means that the cache *MUST NOT* intentionally store the information in non-volatile storage and *MUST* make a best-effort attempt to remove the information from volatile storage as promptly
as possible after forwarding it.[¶](#rfc.section.5.2.2.5.p.2)

This directive is not a reliable or sufficient mechanism for ensuring privacy. In
particular, malicious or compromised caches might not recognize or obey this directive,
and communications networks might be vulnerable to eavesdropping.[¶](#rfc.section.5.2.2.5.p.3)

Note that the must-understand cache directive overrides no-store in certain circumstances;
see [Section 5.2.2.3](#cache-response-directive.must-understand "must-understand").[¶](#rfc.section.5.2.2.5.p.4)

##### [5.2.2.6.](#rfc.section.5.2.2.6) [no-transform](#cache-response-directive.no-transform)

The no-transform response directive indicates that an intermediary (regardless of
whether it implements a cache) *MUST NOT* transform the content, as defined in [Section 7.7](rfc9110.html#message.transformations "Message Transformations") of [[HTTP]](#HTTP).[¶](#rfc.section.5.2.2.6.p.1)

##### [5.2.2.7.](#rfc.section.5.2.2.7) [private](#cache-response-directive.private)

Argument syntax:[¶](#rfc.section.5.2.2.7.p.1)

- #[field-name](#imported.rules)

The unqualified private response directive indicates that a shared cache *MUST NOT* store the response (i.e., the response is intended for a single user). It also indicates
that a private cache *MAY* store the response, subject to the constraints defined in [Section 3](#response.cacheability "Storing Responses in Caches"), even if the response would not otherwise be heuristically cacheable by a private
cache.[¶](#rfc.section.5.2.2.7.p.3)

If a qualified private response directive is present, with an argument that lists
one or more field names, then only the listed header fields are limited to a single
user: a shared cache *MUST NOT* store the listed header fields if they are present in the original response but *MAY* store the remainder of the response message without those header fields, subject the
constraints defined in [Section 3](#response.cacheability "Storing Responses in Caches").[¶](#rfc.section.5.2.2.7.p.4)

The field names given are not limited to the set of header fields defined by this
specification. Field names are case-insensitive.[¶](#rfc.section.5.2.2.7.p.5)

This directive uses the quoted-string form of the argument syntax. A sender *SHOULD NOT* generate the token form (even if quoting appears not to be needed for single-entry
lists).[¶](#rfc.section.5.2.2.7.p.6)

**Note:** This usage of the word "private" only controls where the response can be stored; it
cannot ensure the privacy of the message content. Also, the qualified form of the
directive is often handled by caches as if an unqualified private directive was received;
that is, the special handling for the qualified form is not widely implemented.[¶](#rfc.section.5.2.2.7.p.7.1)

##### [5.2.2.8.](#rfc.section.5.2.2.8) [proxy-revalidate](#cache-response-directive.proxy-revalidate)

The proxy-revalidate response directive indicates that once the response has become
stale, a shared cache *MUST NOT* reuse that response to satisfy another request until it has been successfully validated
by the origin, as defined by [Section 4.3](#validation.model "Validation"). This is analogous to must-revalidate ([Section 5.2.2.2](#cache-response-directive.must-revalidate "must-revalidate")), except that proxy-revalidate does not apply to private caches.[¶](#rfc.section.5.2.2.8.p.1)

Note that proxy-revalidate on its own does not imply that a response is cacheable.
For example, it might be combined with the public directive ([Section 5.2.2.9](#cache-response-directive.public "public")), allowing the response to be cached while requiring only a shared cache to revalidate
when stale.[¶](#rfc.section.5.2.2.8.p.2)

##### [5.2.2.9.](#rfc.section.5.2.2.9) [public](#cache-response-directive.public)

The public response directive indicates that a cache *MAY* store the response even if it would otherwise be prohibited, subject to the constraints
defined in [Section 3](#response.cacheability "Storing Responses in Caches"). In other words, public explicitly marks the response as cacheable. For example,
public permits a shared cache to reuse a response to a request containing an Authorization
header field ([Section 3.5](#caching.authenticated.responses "Storing Responses to Authenticated Requests")).[¶](#rfc.section.5.2.2.9.p.1)

Note that it is unnecessary to add the public directive to a response that is already
cacheable according to [Section 3](#response.cacheability "Storing Responses in Caches").[¶](#rfc.section.5.2.2.9.p.2)

If a response with the public directive has no explicit freshness information, it
is heuristically cacheable ([Section 4.2.2](#heuristic.freshness "Calculating Heuristic Freshness")).[¶](#rfc.section.5.2.2.9.p.3)

##### [5.2.2.10.](#rfc.section.5.2.2.10) [s-maxage](#cache-response-directive.s-maxage)

Argument syntax:[¶](#rfc.section.5.2.2.10.p.1)

- [delta-seconds](#delta-seconds) (see [Section 1.2.2](#delta-seconds "Delta Seconds"))

The s-maxage response directive indicates that, for a shared cache, the maximum age
specified by this directive overrides the maximum age specified by either the max-age
directive or the [Expires](#field.expires) header field.[¶](#rfc.section.5.2.2.10.p.3)

The s-maxage directive incorporates the semantics of the proxy-revalidate response
directive ([Section 5.2.2.8](#cache-response-directive.proxy-revalidate "proxy-revalidate")) for a shared cache. A shared cache *MUST NOT* reuse a stale response with s-maxage to satisfy another request until it has been
successfully validated by the origin, as defined by [Section 4.3](#validation.model "Validation"). This directive also permits a shared cache to reuse a response to a request containing
an Authorization header field, subject to the above requirements on maximum age and
revalidation ([Section 3.5](#caching.authenticated.responses "Storing Responses to Authenticated Requests")).[¶](#rfc.section.5.2.2.10.p.4)

This directive uses the token form of the argument syntax: e.g., 's-maxage=10' not
's-maxage="10"'. A sender *MUST NOT* generate the quoted-string form.[¶](#rfc.section.5.2.2.10.p.5)

#### [5.2.3.](#rfc.section.5.2.3) [Extension Directives](#cache.control.extensions)

The Cache-Control header field can be extended through the use of one or more extension
cache directives. A cache *MUST* ignore unrecognized cache directives.[¶](#rfc.section.5.2.3.p.1)

Informational extensions (those that do not require a change in cache behavior) can
be added without changing the semantics of other directives.[¶](#rfc.section.5.2.3.p.2)

Behavioral extensions are designed to work by acting as modifiers to the existing
base of cache directives. Both the new directive and the old directive are supplied,
such that applications that do not understand the new directive will default to the
behavior specified by the old directive, and those that understand the new directive
will recognize it as modifying the requirements associated with the old directive.
In this way, extensions to the existing cache directives can be made without breaking
deployed caches.[¶](#rfc.section.5.2.3.p.3)

For example, consider a hypothetical new response directive called "community" that
acts as a modifier to the private directive: in addition to private caches, only a
cache that is shared by members of the named community is allowed to cache the response.
An origin server wishing to allow the UCI community to use an otherwise private response
in their shared cache(s) could do so by including[¶](#rfc.section.5.2.3.p.4)

```
Cache-Control: private, community="UCI"
```

A cache that recognizes such a community cache directive could broaden its behavior
in accordance with that extension. A cache that does not recognize the community cache
directive would ignore it and adhere to the private directive.[¶](#rfc.section.5.2.3.p.6)

New extension directives ought to consider defining:[¶](#rfc.section.5.2.3.p.7)

- What it means for a directive to be specified multiple times,
- When the directive does not take an argument, what it means when an argument is present,
- When the directive requires an argument, what it means when it is missing, and
- Whether the directive is specific to requests, specific to responses, or able to be
  used in either.

#### [5.2.4.](#rfc.section.5.2.4) [Cache Directive Registry](#cache.directive.registry)

The "Hypertext Transfer Protocol (HTTP) Cache Directive Registry" defines the namespace
for the cache directives. It has been created and is now maintained at <https://www.iana.org/assignments/http-cache-directives>.[¶](#rfc.section.5.2.4.p.1)

A registration *MUST* include the following fields:[¶](#rfc.section.5.2.4.p.2)

- Cache Directive Name
- Pointer to specification text

Values to be added to this namespace require IETF Review (see [[RFC8126]](#RFC8126), [Section 4.8](https://www.rfc-editor.org/rfc/rfc8126.html#section-4.8)).[¶](#rfc.section.5.2.4.p.4)

### [5.3.](#rfc.section.5.3) [Expires](#field.expires)

The "Expires" response header field gives the date/time after which the response is
considered stale. See [Section 4.2](#expiration.model "Freshness") for further discussion of the freshness model.[¶](#rfc.section.5.3.p.1)

The presence of an Expires header field does not imply that the original resource
will change or cease to exist at, before, or after that time.[¶](#rfc.section.5.3.p.2)

The Expires field value is an HTTP-date timestamp, as defined in [Section 5.6.7](rfc9110.html#http.date "Date/Time Formats") of [[HTTP]](#HTTP). See also [Section 4.2](#expiration.model "Freshness") for parsing requirements specific to caches.[¶](#rfc.section.5.3.p.3)

```
  Expires = HTTP-date
```

For example[¶](#rfc.section.5.3.p.5)

```
Expires: Thu, 01 Dec 1994 16:00:00 GMT
```

A cache recipient *MUST* interpret invalid date formats, especially the value "0", as representing a time in
the past (i.e., "already expired").[¶](#rfc.section.5.3.p.7)

If a response includes a [Cache-Control](#field.cache-control) header field with the max-age directive ([Section 5.2.2.1](#cache-response-directive.max-age "max-age")), a recipient *MUST* ignore the Expires header field. Likewise, if a response includes the s-maxage directive
([Section 5.2.2.10](#cache-response-directive.s-maxage "s-maxage")), a shared cache recipient *MUST* ignore the Expires header field. In both these cases, the value in Expires is only
intended for recipients that have not yet implemented the Cache-Control header field.[¶](#rfc.section.5.3.p.8)

An origin server without a clock ([Section 5.6.7](rfc9110.html#http.date "Date/Time Formats") of [[HTTP]](#HTTP)) *MUST NOT* generate an Expires header field unless its value represents a fixed time in the past
(always expired) or its value has been associated with the resource by a system with
a clock.[¶](#rfc.section.5.3.p.9)

Historically, HTTP required the Expires field value to be no more than a year in the
future. While longer freshness lifetimes are no longer prohibited, extremely large
values have been demonstrated to cause problems (e.g., clock overflows due to use
of 32-bit integers for time values), and many caches will evict a response far sooner
than that.[¶](#rfc.section.5.3.p.10)

### [5.4.](#rfc.section.5.4) [Pragma](#field.pragma)

The "Pragma" request header field was defined for HTTP/1.0 caches, so that clients
could specify a "no-cache" request (as [Cache-Control](#field.cache-control) was not defined until HTTP/1.1).[¶](#rfc.section.5.4.p.1)

However, support for Cache-Control is now widespread. As a result, this specification
deprecates Pragma.[¶](#rfc.section.5.4.p.2)

**Note:** Because the meaning of "Pragma: no-cache" in responses was never specified, it does
not provide a reliable replacement for "Cache-Control: no-cache" in them.[¶](#rfc.section.5.4.p.3.1)

### [5.5.](#rfc.section.5.5) [Warning](#field.warning)

The "Warning" header field was used to carry additional information about the status
or transformation of a message that might not be reflected in the status code. This
specification obsoletes it, as it is not widely generated or surfaced to users. The
information it carried can be gleaned from examining other header fields, such as [Age](#field.age).[¶](#rfc.section.5.5.p.1)

## [6.](#rfc.section.6) [Relationship to Applications and Other Caches](#history.lists)

Applications using HTTP often specify additional forms of caching. For example, Web
browsers often have history mechanisms such as "Back" buttons that can be used to
redisplay a representation retrieved earlier in a session.[¶](#rfc.section.6.p.1)

Likewise, some Web browsers implement caching of images and other assets within a
page view; they may or may not honor HTTP caching semantics.[¶](#rfc.section.6.p.2)

The requirements in this specification do not necessarily apply to how applications
use data after it is retrieved from an HTTP cache. For example, a history mechanism
can display a previous representation even if it has expired, and an application can
use cached data in other ways beyond its freshness lifetime.[¶](#rfc.section.6.p.3)

This specification does not prohibit the application from taking HTTP caching into
account; for example, a history mechanism might tell the user that a view is stale,
or it might honor cache directives (e.g., Cache-Control: no-store).[¶](#rfc.section.6.p.4)

However, when an application caches data and does not make this apparent to or easily
controllable by the user, it is strongly encouraged to define its operation with respect
to HTTP cache directives so as not to surprise authors who expect caching semantics
to be honored. For example, while it might be reasonable to define an application
cache "above" HTTP that allows a response containing Cache-Control: no-store to be
reused for requests that are directly related to the request that fetched it (such
as those created during the same page load), it would likely be surprising and confusing
to users and authors if it were allowed to be reused for requests unrelated in any
way to the one from which it was obtained.[¶](#rfc.section.6.p.5)

## [7.](#rfc.section.7) [Security Considerations](#security.considerations)

This section is meant to inform developers, information providers, and users of known
security concerns specific to HTTP caching. More general security considerations are
addressed in "HTTP/1.1" ([Section 11](rfc9112.html#security.considerations "Security Considerations") of [[HTTP/1.1]](#HTTP11)) and "HTTP Semantics" ([Section 17](rfc9110.html#security.considerations "Security Considerations") of [[HTTP]](#HTTP)).[¶](#rfc.section.7.p.1)

Caches expose an additional attack surface because the contents of the cache represent
an attractive target for malicious exploitation. Since cache contents persist after
an HTTP request is complete, an attack on the cache can reveal information long after
a user believes that the information has been removed from the network. Therefore,
cache contents need to be protected as sensitive information.[¶](#rfc.section.7.p.2)

In particular, because private caches are restricted to a single user, they can be
used to reconstruct a user's activity. As a result, it is important for user agents
to allow end users to control them, for example, by allowing stored responses to be
removed for some or all origin servers.[¶](#rfc.section.7.p.3)

### [7.1.](#rfc.section.7.1) [Cache Poisoning](#cache.poisoning)

Storing malicious content in a cache can extend the reach of an attacker to affect
multiple users. Such "cache poisoning" attacks happen when an attacker uses implementation
flaws, elevated privileges, or other techniques to insert a response into a cache.
This is especially effective when shared caches are used to distribute malicious content
to many clients.[¶](#rfc.section.7.1.p.1)

One common attack vector for cache poisoning is to exploit differences in message
parsing on proxies and in user agents; see [Section 6.3](rfc9112.html#message.body.length "Message Body Length") of [[HTTP/1.1]](#HTTP11) for the relevant requirements regarding HTTP/1.1.[¶](#rfc.section.7.1.p.2)

### [7.2.](#rfc.section.7.2) [Timing Attacks](#security.timing)

Because one of the primary uses of a cache is to optimize performance, its use can
"leak" information about which resources have been previously requested.[¶](#rfc.section.7.2.p.1)

For example, if a user visits a site and their browser caches some of its responses
and then navigates to a second site, that site can attempt to load responses it knows
exist on the first site. If they load quickly, it can be assumed that the user has
visited that site, or even a specific page on it.[¶](#rfc.section.7.2.p.2)

Such "timing attacks" can be mitigated by adding more information to the cache key,
such as the identity of the referring site (to prevent the attack described above).
This is sometimes called "double keying".[¶](#rfc.section.7.2.p.3)

### [7.3.](#rfc.section.7.3) [Caching of Sensitive Information](#caching.of.sensitive.information)

Implementation and deployment flaws (often led to by the misunderstanding of cache
operation) might lead to the caching of sensitive information (e.g., authentication
credentials) that is thought to be private, exposing it to unauthorized parties.[¶](#rfc.section.7.3.p.1)

Note that the Set-Cookie response header field [[COOKIE]](#COOKIE) does not inhibit caching; a cacheable response with a Set-Cookie header field can
be (and often is) used to satisfy subsequent requests to caches. Servers that wish
to control caching of these responses are encouraged to emit appropriate Cache-Control
response header fields.[¶](#rfc.section.7.3.p.2)

## [Appendix B.](#rfc.section.B) [Changes from RFC 7234](#changes.from.rfc.7234)

Handling of duplicate and conflicting cache directives has been clarified. ([Section 4.2.1](#calculating.freshness.lifetime "Calculating Freshness Lifetime"))[¶](#rfc.section.B.p.1)

Cache invalidation of the URIs in the Location and Content-Location header fields
is no longer required but is still allowed. ([Section 4.4](#invalidation "Invalidating Stored Responses"))[¶](#rfc.section.B.p.2)

Cache invalidation of the URIs in the Location and Content-Location header fields
is disallowed when the origin is different; previously, it was the host. ([Section 4.4](#invalidation "Invalidating Stored Responses"))[¶](#rfc.section.B.p.3)

Handling invalid and multiple Age header field values has been clarified. ([Section 5.1](#field.age "Age"))[¶](#rfc.section.B.p.4)

Some cache directives defined by this specification now have stronger prohibitions
against generating the quoted form of their values, since this has been found to create
interoperability problems. Consumers of extension cache directives are no longer required
to accept both token and quoted-string forms, but they still need to parse them properly
for unknown extensions. ([Section 5.2](#field.cache-control "Cache-Control"))[¶](#rfc.section.B.p.5)

The public and private cache directives were clarified, so that they do not make responses
reusable under any condition. ([Section 5.2.2](#cache-response-directive "Response Directives"))[¶](#rfc.section.B.p.6)

The must-understand cache directive was introduced; caches are no longer required
to understand the semantics of new response status codes unless it is present. ([Section 5.2.2.3](#cache-response-directive.must-understand "must-understand"))[¶](#rfc.section.B.p.7)

The Warning response header was obsoleted. Much of the information supported by Warning
could be gleaned by examining the response, and the remaining information — although
potentially useful — was entirely advisory. In practice, Warning was not added by
caches or intermediaries. ([Section 5.5](#field.warning "Warning"))[¶](#rfc.section.B.p.8)
