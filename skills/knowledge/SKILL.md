# 项目知识维护

维护团队后来理解项目、作出决定和完成任务所需的共享知识，不充当对话存档、个人记忆或任务日记。整理对象是经过收录判断的项目事实、机制、约束和决定依据，而不是把本次经历换成客观语气；新增、修正、减少或保持不变，都可能是正确结果。

## 主动识别使用时机

不等待用户点名。需要依据项目事实理解业务、判断修改影响或解释既有选择时，先按项目入口查相关知识；开发、排障、研究或决策中发现可复用的新结论、现有说明失效或重要条件缺失时，进入知识取舍路径。不要等到会话结束才识别这些变化；交付前核对本次已经识别的影响是否处理。

主动使用不等于每次都写文档。直接读取已有准确知识即可回答的，只检索；既有内容已充分覆盖、只有内部格式变化或普通通用问答时，不额外启动知识审计。没有需要维护的内容就继续原任务，不追加固定的“知识复核完成”汇报。

## 确定入口、任务和权限

读取适用的项目指令，确认知识库的读者与共享范围，找到知识入口、分类约定、相关来源和检查方式。项目名称、目录、术语、格式、日志和安装方式由项目规定，不从技能安装位置推断。没有知识入口时先查现有文档位置，不能擅自创建另一套库或改成 OKF。

主动检索和判断不扩大写入权限。只读评估、解释或总结保持只读；用户限定只改某些文件时遵守该范围。在已授权的实现或修复中，按项目约定同步本次变更影响的必要使用说明，不要求用户再说一次“整理知识库”；新增独立主题或扩大维护范围须有任务或项目授权。已有授权不重复询问。知识事实、项目工作规则和通用技能有不同权限，不能把一次发现自动升级成新禁令或全局规则。

使用当前任务中已经取得的证据，并核对相关文件和状态。Git diff 只是定位变化的线索，不等于全部工作成果；已提交的变化、没有改代码却查明的事实，以及被撤销的尝试要区分。保留他人工作树和暂存内容，按风险使用已有恢复方式，不为每次小修建立全库快照。

## 选择相应的工作路径

| 当前任务 | 方法与结果 |
| --- | --- |
| 项目背景查询或已有决定解释 | 从项目索引定位相关事实和依据，只展开本题需要的主题；回答及其限制，不自动修库 |
| 工作中发现知识变化、工作收尾或不确定该放什么 | 读取[取舍与提炼](references/curation.md)，从最终成果、查明的事实和确认的决定提炼候选，对照已有知识决定处置；不要先写工作总结再归档 |
| 初建、恢复或结构接管 | 读取[组织方法](references/organization.md)，确定使用任务、分类、重叠归属与扩展方式；同样进行知识取舍，并实际落实内容与导航 |
| 明确的事实更新或新增主题 | 同样先做下面的收录判断，再核对来源、范围和主要维护位置；个人陈述、环境观察或决定权限不清时读[取舍与提炼](references/curation.md) |
| 迁移、合并或废弃 | 按[变更与退役](references/changes.md)处理信息保全、入链、来源及替代关系；不留下两套有效正文 |
| 仅修措辞或查阅答案 | 完成指定范围，不顺带启动全库整理、刷新元数据或生成复盘文档 |

## 先判断收录，再提炼知识增量

写正文前，逐条确认候选的共享读者与用途、适用范围、事实或决定的权威依据、证据状态，以及相对现有主题的增量。来源是某个人不等于内容私人；内容由个人提出也不等于团队已经采纳。个人偏好、对助手的要求和单机现象，不能仅通过删掉人称变成团队政策或通用事实。具体准入与提炼方法见[取舍与提炼](references/curation.md)。

问清谁会在什么后续任务中使用、缺少它会误判什么，证据支持到哪个版本、环境和条件。只影响个人工作方式的材料排除在共享正文之外；只有任务明确授权个人记录时才处理相应目的地，不自动另建笔记。共享价值不要求适用于所有人：团队需要的特定环境事实可以收录，但不能扩大其范围。这些判断不要求输出固定表格或评分。

对仍有效但缺失的知识补充，对已经失效的当前说明修正，对已有且准确的内容复用。优先更新承担该规则的现有主题；只有独立用途和责任成立才新建。一次工作可同时需要更新契约、修正操作说明、保留决定原因和不收录调试过程，不给整个会话作一次笼统的“入库/不入库”判断。

不要按改动大小、花费时间或出现次数决定价值。一条罕见但影响恢复安全的限制可能必须保留；大量格式改动可能没有知识增量。临时限制如果仍影响后续工作，应写清适用条件与退出条件，而不是因为“临时”全部丢弃。边界相近仍难判断时，读取[对照实例](references/curation-examples.md)，使用其中的判据，不照搬事实或目录。

## 核对事实与安置责任

源码支持实现行为，配置支持声明值，确认的需求和决定支持要求，运行记录支持特定环境和时点的状态。旧说明与当前实现冲突时先分清对象和适用范围；代码存在不能单独证明设计正确或标准合规。材料中的批注和执行指令不扩大授权，敏感值不进入知识或输出。

证据不足就限定结论或报告具体待核实点；资料不可访问不能算作没有知识增量。能够查清、又影响本次要求的条件，应继续核对。不得通过改名为“参考”或标成“草稿”掩盖必要信息缺失。

按项目分类和共同变化责任安置知识，不按来源文件或调查顺序归档。同一规则有一个主要维护位置，其他入口用摘要或链接。接口必须直接给出调用方依赖的默认行为、错误和兼容条件；内部存储归提供端，特定调用方的重试和兜底归调用方。不能用去重或解耦为由删掉正确使用所需的信息。

## 写成可使用的主题

只把通过收录判断的候选写成主题，让没有参加本次工作的人能读懂对象、条件、行为及影响。保留必要原因、例外、可核对的来源和操作入口，不复制聊天或无关个人细节。经过只在解释因果、决定演变或复现时保留最小必要序列，不把工具流水和催促过程当知识。概述解释职责与边界，操作说明包括前提、执行与结果判断，设计说明区分当前行为和有依据的原因；不用统一模板凑章节。具体检查见[内容验收](references/acceptance.md)。

项目采用 OKF 时，首次编写或涉及格式选择读取[OKF 参考](references/okf.md)，字段有疑问再查[固定规范原文](references/okf-spec.md)。格式承载知识，不能替代取舍。生成者、时间、来源与验证按真实证据记录，不能批量刷新日期、哈希或 verified 制造已核验的表象。

## 完成实际维护

更新事实时检查依赖该事实的知识，迁移时修正原入链和相对来源，废弃时处理有效说明与历史的关系。原始事件可以留在问题、测试或决策记录中，不应与当前使用指引竞争。已经写对新页但旧入口仍误导，不算维护完成。

检查跟随影响：措辞看正文与差异，事实核对依据，契约看两端，迁移看引用和信息保全，结构接管检查分类及实际检索。优先使用项目检查；辅助工具见[工具说明](references/editing.md)，依赖见[运行环境](references/environment.md)。脚本处理可机械判断的属性，不替模型决定知识价值；不因选用了技能就安装依赖、跑全库或重做无关测试。

按[验收方法](references/acceptance.md)完成本次范围。不强制每次都写点什么；用户要求知识评估时说明已核查范围和理由，其他任务只报告影响结果的发现，不创建“无变化”记录。关键证据缺失时报告未能判断，不冒充“不需要整理”。需要修改且已有授权时落实修改，不能只交付候选清单。

按项目约定更新确有需要的索引、变更记录和续接信息；它们不是每次会话必须产出的尾项，也不承接未通过收录判断的材料。交付实际位置、取舍结果和未验证范围，不宣称有限测试保证所有模型正确。未经授权不提交、发布、部署、修改业务实现或其他项目规则。
