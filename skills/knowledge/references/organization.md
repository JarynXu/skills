# 建立与维护分类

用于初建、结构接管或分类本身发生变化。日常编辑只读取项目已有归属约定，不重走设计过程。

## 形成可执行的组织规则

先确认使用者和实际问题：理解业务、定位修改、查接口、完成操作、解释决定分别需要什么知识。调查项目的责任对象、组成和已有资料，不按自己阅读仓库的先后创建顶层分类，也不把缺少资料当成缺少业务。

盘点材料时分开三件事：哪些事实有用、现有文档是否完整、归属是否合适。有效事实可以保留，但不能因为正文写过就保留失当结构；结构合理的文档也不必为统一外观重写。

选择一个主要组织依据，例如业务对象、系统责任或工程使用目的。为每个主类说明收纳、不收纳、相邻边界和新内容的判断条件。不是只写几个目录名或“按需归档”。同一事实跨视角出现时，确定谁保存完整规则，其他入口用摘要或链接。没有足够分类依据，继续调查；不要先把内容放进临时杂项再等以后整理。

用现有的重叠主题验证规则：一个跨对象流程、一份公共约束、一份对象内部设计、一个接口、一个操作任务、一项历史决定，各自应能找到有理由的归属。如果多个位置都说得通，明确判定顺序或合并边界。归属可以依任务语义区分，不能只看标题关键词或来源路径。

把该项目选定的规则保存在项目约定或知识入口可达的位置。通用技能不保存项目目录表；项目没有复杂度时，一段清楚的入口说明足够。初建交付需要实际目录、有效导航和现有内容落位，不能止于推荐结构。未调查主题可以记录覆盖范围，但不生成猜测正文或空壳百科。

## 适用的参考视角

| 方法 | 用途与限制 |
| --- | --- |
| SWEBOK 知识领域 | 检查需求、架构、测试、运行、维护、配置管理等工程知识是否遗漏；不是必须建齐的学科目录。 |
| arc42 架构视角 | 区分系统上下文、内部构成、运行交互、部署、共同机制与决策；不要给每个组件复制全部章节。 |
| 项目管理中的 WBS | 借鉴产物范围和责任分解，不把任务排期或迭代号当长期知识的唯一分类。 |
| Diátaxis 阅读目的 | 判断需要教程、操作指南、参考还是解释；帮助写文档，不要求每层再分四个空目录。 |

这些视角可以检查同一个结构，但不应各维护一份事实副本。非软件项目按实际业务、研究对象、产物和责任组织，不制造不存在的 services 或 API。

## 处理常见重叠

业务概念说明对象和规则；系统流程说明多个责任对象怎样共同完成工作；组件说明内部职责和机制；接口说明消费者必须知道的行为；操作指南说明人在给定条件下怎样完成任务。先问这篇文档服务什么问题，再选主要维护位置。

安全、数据、配置和测试不是天然只能归一个顶层的主题：系统共同约束、组件实现与执行步骤有不同归属。只读者视角变化时增加导航，不复制正文；规则本身具有独立责任时才拆开。

对一个提供端，接口契约和内部实现可以同属该组件的不同子主题；也可按项目约定使用独立契约目录。选择后应一致，不能让每个维护者自行选一种。共享协议、跨组件流程不因为由某个仓库首先实现就变成该仓库的私有知识。

## 新增、拆分与结构改变

已有主题能容纳且一起变化，就补现有文档。子主题能独立使用、独立维护，并且上层已经出现多种责任时，建立子目录和明确入口。不要以行数或文件数单独决定拆分。深度过大导致普通任务连续跳转时，应合并过度拆分的内容。

新增子主题遵循既有规则。改变主分类或责任边界时，评估整个受影响集合，更新项目约定、实际内容和入口，清除相互冲突的旧归属；不是在新目录旁保留一套同等权威的旧库。普通小修改遇到全局结构问题时，说明影响并遵循当前授权范围，不私自扩展重构。

## 结构验收

结构是否成立，看新维护者能否根据规则放置同类知识，读者能否从实际问题找到内容，变化是否只触及必要的维护位置。主要分类必须覆盖已知责任与明确的扩展情况，不以“当前只有几篇”免除设计。

一份职责清楚的文档不需要未来永不移动才能算完成；日后因为真实业务变化调整结构，与今天把已知边界含糊留给以后，是不同情形。
