# 内容与任务验收

检验用户要求的完整范围，不按文件数量、语气自信或脚本退出码判断。没有必要每次输出一份验收报告，但应实际执行相应检查。

## 各种文档应能回答的问题

| 用途 | 判断完成的内容 |
| --- | --- |
| 项目或组件概述 | 为谁解决什么问题、承担与不承担哪些职责、参与对象及主要关系、继续查阅与代码定位入口 |
| 业务概念与规则 | 术语与对象、适用范围、条件、结果及边界，能区分要求和实现 |
| 接口契约 | 调用对象、必填/可选输入、缺省与取值限制、正常结果、零值/缺失语义、错误和兼容边界，调用方无需追实现才能正确使用 |
| 操作指南 | 前置条件、必要参数与权限、选择与执行步骤、预期结果、如何确认结果、失败时影响与恢复边界；没有擅自执行现场操作 |
| 设计或实现解释 | 责任与数据归属、主要流程、重要约束/分支、对其他部分的影响，有证据的原因及代码定位 |
| 已知问题与决定 | 条件、影响、依据、当前处理或明确选择、适用状态及替代关系，不伪造批准过程 |

不是要求每篇都出现这些标题。使用自然结构回答相应问题，避免过度拆分和重复；没有独立用途的几个句子可以合并。

## 按任务核验

初建/结构接管：对已知内容和预计责任类别都有可执行归属；项目入口能到达正文与约定；现有正文已实际落位；缺少覆盖的领域明确记录，不能靠缺少文件掩盖分类含糊。

事实更新：相关依据已核实，主要结论及真正受影响的派生知识一致；旧说明不会继续误导。迁移/退役：引用、来源和入口已处理，有用内容没有丢失，历史与替代关系明确。小修：本次表达问题解决且语义、来源、元数据和其他文件无不必要变化。

选真实使用问题做检索和执行推演，例如定位一项功能应该改谁、解释默认行为、选择更新配置的方法、归档一条新规则。必须能给出有据的答案；存在同等可能的归属或关键操作条件缺失，就继续修正。

确定性检查使用已有工具：格式、链接、声明来源、规则副本、禁止越界和迁移集合。工具没有覆盖的语义需要读实际文档和证据。断言要指向结果，不要求固定措辞；不要把“有一个错误处理章节”当成错误语义完整。

## 工作后复核的结果

按[收录判断](curation.md#写入前判断收录资格)逐条对照来源与最终正文：去掉说话者后，主张的适用范围和决定权是否仍有依据？不能把个人要求写成团队规则、单机观察写成环境通则、已接受方案写成已实施状态。重点看共享用途、现有表达与证据是否支持处置，不以客观语气、新增条数或特定标题判定正确。

对有增量的材料，检查是否更新了其主要主题，而非追加会话总结；来源是否可核对而未泄露无关个人内容。对不收录的材料，确认不是仅因来自个人、限定某环境或包含历史就拒绝，也没有遗漏关键条件、短期限制、有效因果时间线，或因缺少访问权限而未核查。已经被准确信息覆盖与无法判断必须区分。混合任务允许不同结论分别更新、引用、退役或不保存。

只读请求的结果是有依据的建议；授权维护的结果必须体现到实际文件。没有必要变更时保持不变，不创建空的复盘、日志或“无变化”页面。规则修改有独立权限，不能用知识提炼代替政策批准。

## 交付边界

内部可以多次修订验证，但已知结构性缺陷、错误事实、断链、信息丢失和关键条件遗漏不得留作正式交付的欠账。把不完整主题改名为参考，或声明未来再补，不等于完成原要求。

没有执行的环境测试和跨模型试验如实记录；脚本测试不能代替真实模型完成任务。客观未知可以明确表达，本次任务所需的验证条件缺失则说明未满足的验收项，不能造通过记录。

交付文件与已报告内容一致，清除临时写作脚手架，项目配置和他人工作保持完整。除明确要求外不追加提交、发布、部署、全局安装或无关业务修复。
