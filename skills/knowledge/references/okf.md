# OKF 定位说明

仅在项目采用 OKF 且需要确认格式时使用。固定原文版本、提交及许可证见 `okf-origin.json`；需要精确语义再读 `okf-spec.md` 对应章节，不每次加载全文。

| 问题 | 原文章节 |
| --- | --- |
| 概念文件和元数据 | §4 |
| 来源与逐条归因 | §5.1 |
| 生成与验证 | §5.2—§5.3 |
| 生命周期 | §5.4 |
| 链接与作者身份 | §6—§7 |
| 索引和日志 | §8—§9 |
| 最小支持与版本 | §11—§12 |

UTF-8 Markdown、YAML frontmatter 中的 `type` 是概念文件的基础要求；title、description、generated、verified、sources 等按语义和项目约定使用。未知 type 和扩展字段应保留，不因不认识而删除。没有规定所有文档的固定章节。

`index.md`、`log.md` 是可选导航和历史形式；子目录 index 没有 frontmatter，根 index 可以声明 okf_version。日期日志按 YYYY-MM-DD 分组倒序，日志数量和提交前合并方式由项目规定。

sources 条目需要 resource；正文对重要外部事实逐条归因时，用稳定的 sources.id 与同名脚注关联，不用数组位置。一般背景不需要堆叠同一脚注，普通解释性脚注也不必伪装成外部来源。resource 可指向文件、URL 或群体描述；`kind: scope` 是辅助工具识别群体描述的扩展，不是标准必填。

相对路径以当前文档为基准，`/` 以 bundle 根为基准。项目引用外部本地来源时，需要为工具明确允许读取的 workspace；规范的链接语义不等于运行环境自动授予读取权限。

sha256 是可选扩展，不要求每份知识计算或维护来源哈希。generated 记录真实生成者，verified 记录确实发生的验证；单个 verified 映射与映射列表均可。不得为填字段编造作者、日期或验证。存在时间戳时使用明确 UTC offset；stale_after 是绝对时点，不是统一强制保质期。

文字修订不应刷新无关文件的来源或验证时间。项目选择更严格的字段、索引或日志约束时，在项目维护，不将其说成 OKF 全局规则。

随技能的检查器支持核心语法和本地引用一致性，不执行计算证明或外部程序，也不联网验证 URL。断链是维护问题，不等于任何消费者必须拒绝整个 bundle；检查报告不是 OKF 通用合规认证。
