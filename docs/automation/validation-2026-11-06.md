# 多会话监听验证

改前的 iCenter、watcher 和组合文档对应提交 `1b1612e963b9e5a95a68d11483e10e0a7b0ebc60`。改后演练使用本机安装的两个技能包，包内变更文件已与仓库候选逐一核对。环境为 Windows、Node.js 26.12.1 和 iCenter 12.6.8.13。

## 同一客户端上的三个订阅

在已登录的主窗口里，用 watcher 的标准 CLI 和三个独立状态目录启动三个实例。甲、乙分别绑定一个已核对的联系人，第三个实例也观察甲。测试按注册名从客户端 SDK 取出这三个观察者，只向它们传入合成的到达通知。桌面投递端使用本地 MCP 替身和临时目标 ID。

- 空闲期间投递次数为零。甲的第一条通知分别出现在第一和第三个实例的事件文件中，乙的通知仅出现在第二个实例。列表能按目标 ID 找回配置、原生所有者和最近采集时间。
- 暂停乙后投递一条测试通知，原生缓冲显示一条待取。用原配置恢复后，所有者和代次相同，缓冲中的消息投给乙。随后彻底结束乙，再发给甲的通知仍交给其余两个实例。
- 共核对六次测试投递。结束后验证三个测试订阅均已移除。另用真实宿主的应用工具服务只读核对了本地 Codex 目标。真人来信及实际唤醒业务聊天未纳入本次演练。

原生回归覆盖旧单槽与新订阅共存、独立确认、陈旧代次、结束时输出或确认失败后的恢复。watcher 回归覆盖异目录并发启动、同目录单写者、实例登记、配置与目标不匹配时拒绝停止，以及投递结果未知时避免重发。

## 首次使用

同一模型分别从基线和候选的已安装包接到同一请求。任务要求两个聊天分别关注甲乙、随时查归属、单独结束其中一个，另有每周五的定时检查。两次都只读技能文档、CLI 帮助及宿主工具说明，未启动监听或创建计划。

基线选择了包外组合入口，用一个原生所有者向两个目标分流，指出单独停止一项需要停整组并重配。候选选择两个标准 watcher 实例，给出了 `list --thread`、`subscriptions`、按配置暂停和按接收器目录结束的命令。两次均将周五的时间要求单独交给宿主调度。此比较覆盖本条复合请求。
