# Skill 实现标准

本文规定如何把一个专业角色或重复工作实现为可移植 Skill。仓库目录、frontmatter 和提交命令的基础契约以 [AGENTS.md](../../AGENTS.md) 与 [CONTRIBUTING.md](../../CONTRIBUTING.md) 为准。

## 建立行为边界

实现前用具体任务确认：

- 哪些用户表达应触发 Skill；
- Agent 在任务中承担什么责任和 authority；
- 哪些决定属于产品、设计、架构、工程或其他专业所有者；
- 哪些输出、外部写入和副作用在授权范围内；
- 什么证据能证明完成，而不只是证明执行过步骤。

将角色建模为稳定职责和判断能力，不要模拟资历、人格台词或虚构组织权力。任务只需要某项局部能力时，不强迫 Agent 生成该职业的完整产物体系。

## 将内容放入正确位置

| 内容 | 位置 | 要求 |
|---|---|---|
| 触发范围 | `SKILL.md` frontmatter `description` | 同时说明能力与适用情境，不依赖正文完成触发 |
| 始终适用的责任、流程和完成门槛 | `SKILL.md` | 简洁、命令式、与具体工具产品解耦 |
| 条件性专业知识和变体 | `references/` | 按任务关切组织，并从 `SKILL.md` 直接路由 |
| 脆弱且重复的确定性操作 | `scripts/` | 参数明确、可测试；审计脚本默认只读 |
| 会被复制、填充或交付的资源 | `assets/`，或需要读取其语义时放 `references/` | 区分输出材料与上下文知识 |
| 可选产品界面元数据 | `agents/` | 不得成为 Skill 正确运行的必要条件 |
| 编写经验、测试用例和运行记录 | Skill 目录之外 | 不得污染终端 Agent 的运行时知识 |

不要在 Skill 内添加 README、变更日志、安装指南、实验日志或仅供维护者阅读的 `docs/`。

## 设计 `SKILL.md`

`SKILL.md` 应形成运行时控制面，而不是 reference 摘要：

1. 明确职业责任、范围和不得越过的 authority；
2. 根据任务类型选择工作模式；
3. 给出从输入到验证的核心状态流；
4. 根据可观察的任务关切路由 references；
5. 定义停止条件、完成条件和不确定性处理；
6. 仅保留每次触发都需要的规则。

不要按作者的研究顺序、工具顺序或 reference 目录组织正文。结构应来自任务域中的稳定职责和决策关系。

## 设计渐进披露

- 每个 reference 只承担一个可命名的知识责任。
- 路由条件描述用户任务中的可观察信号，而不是要求 Agent 猜测文件内容。
- `SKILL.md` 必须直接链接可用 reference；不要依赖多层跳转才能发现关键知识。
- 未选择的框架、技术和产物 profile 不得预加载或用于“比较后排除”。
- 加载 reference 只提供判断依据，不自动增加输出章节或扩大任务授权。

当多个变体共享核心工作流时，将选择规则留在 `SKILL.md`，将每个变体的具体契约放入独立 reference。

## 设计可执行要求

对容易失真的要求，至少明确：

- **适用条件**：什么时候必须执行；
- **谓词与作用域**：究竟约束什么，以及适用于哪些对象；
- **状态或 authority**：谁确认、谁仍未知；
- **证据**：通过什么观察、测试或来源判断；
- **失败行为**：不满足时修复、保留开放项还是停止；
- **停止条件**：何时不再拆分、扩展或继续循环。

避免只有“全面、专业、仔细、最佳实践”等不可证伪形容词。不得为了填满模板制造事实、责任人、历史理由、技术选择或批准状态。

## 设计产物生成

把专业知识源与展示产物分开：

```text
权威或任务内知识
+ 输出契约
+ 可选产物 profile
-> 产物
```

固定格式确实影响正确性时提供模板；模板只规定形状和字段语义，不提供项目事实。组织未知时使用明确的默认 profile，不能把熟悉的行业模板冒充成组织标准。

生成前确定适用的来源、输出契约、profile 和完整性条件。将能够随内容决策判断的条件直接用于结构选择、主张纳入、状态标记、关系建立和媒介呈现；不要维护一份同义的“生成规则”和“审计规则”。完整产物形成后，再验证只有在全局上才能判断的关系、依赖外部证据的条件和生成时仍未解决的事项。

验证方式由任务所需证据决定，不按产物篇幅或“复杂”标签自动引入固定循环。需要比较候选版本、独立判定或测试 Skill 首次行为时，可以固定被检版本并使结论只对应该版本；普通产物生成不因此默认增加冻结、重写或全量复审。

## 使用脚本的边界

适合脚本的内容包括格式解析、链接完整性、字段枚举、文件发现、模板结构和其他确定性检查。语义相关性、专业取舍和 authority 判断通常仍需 Agent 或专业人员审查。

脚本输出是证据，不是结论。除非规则本身可完全机械判定，不得因为命令退出码为零就宣称整个 Skill 行为正确。

## 完成实现

完成一个 Skill 至少需要证明：

- 触发描述能够覆盖预期任务且不会明显误触发；
- 核心流程、authority 边界和完成条件明确；
- references 可从 `SKILL.md` 直接发现且按需加载；
- 没有重复或相互改写的权威规则；
- 模板和脚本已经按其真实使用方式验证；
- 静态验证、仓库测试和发现检查通过；
- 复杂行为经过不泄漏答案的前向测试；
- 测试证明的是完整目标，而不是某个方便通过的缩小版本。
