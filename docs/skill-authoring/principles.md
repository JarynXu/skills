# Skill 工程原则

本目录记录如何设计、实现和验证 Skill。它服务于 Skill 作者，不属于任何具体 Skill 的运行时知识，也不应随某个 Skill 安装后参与终端任务。

## 把 Skill 当作行为系统

Skill 的目标不是保存尽可能多的知识，而是让 Agent 在适用任务中稳定地作出专业判断并完成工作。设计时分别处理：

- **触发**：Agent 何时应当加载 Skill；
- **选择**：当前任务需要哪些条件性知识；
- **执行**：Agent 应经过哪些状态和决策；
- **产物**：结果必须满足什么契约；
- **验证**：什么证据足以证明工作完成。

知识完整不等于行为可靠。Agent 能在事后指出错误，却可能在生成时犯同样的错误；遇到这种情况，应改变执行和验证结构，而不是继续重复知识。

## 按风险分配自由度

- 多种方案均可成立且依赖情境判断时，使用原则和启发式规则。
- 存在优选结构但需要局部适配时，使用字段契约、伪代码或参数化模板。
- 格式、顺序、状态转换或验收容易出错时，使用固定模板、确定性脚本或强制工作流。

不要用更多强调语句代替更低自由度的结构。关键概念容易混淆时，为它们建立独立字段；输出形状必须稳定时，给出可直接填写的模板。

## 让渐进披露负责选择

`SKILL.md` 只保留始终适用的职业责任、核心流程、路由条件和完成门槛。详细知识进入按任务关切组织的 `references/`，并由 `SKILL.md` 直接说明何时读取。

渐进披露解决“加载什么”，不保证“是否执行”。如果 Agent 已读取并理解规则，但仍不能稳定遵守，应改进工作流、产物契约或验证器，而不是再次复制该规则。

## 让步骤的目的进入后续行为

Agent 容易把“执行了专业步骤”误认为“实现了专业目的”。要求建立 Foundations、组件、模型、计划或交接物时，必须继续说明后续哪个决定或对象会使用它，以及什么证据能够证明这种使用真的发生。

```text
需要
-> 中间结果
-> 后续消费者
-> 采用或应用
-> 反馈与完成证据
```

共享目录中的组件不等于已复用，读过一次的设计稿不等于持续符合，归档的决定也不等于已经影响实现。角色能够控制消费者时，应实际接入并验证；只能影响其他角色时，应建立真实交接、返回证据或符合性路径，不得越权制造“已经采用”的结论。

这组运行时行为的权威定义位于 [`skill-creator` 的行为模型](../../skills/skill-creator/references/behavior-model.md#carry-purpose-into-adoption)。维护本文时不要建立与其竞争的另一套字段或状态规则。

## 每条规则只有一个权威定义

同一语义不要同时在 `SKILL.md`、多个 reference、模板和检查表中分别展开。选择一个权威位置，其他位置只负责路由、引用或提供结构化槽位。

需要多处出现的术语、状态或标记应保持字符级一致。若不同位置承担不同职责，应明确区分“原则”“具体契约”和“验证方式”，而不是改写同一要求。

## 建模规则，不枚举失败样本

从失败中提炼能够覆盖未知实例的稳定维度、谓词和停止条件。不要把每次测试发现的问题逐条追加成禁止清单。

一条规则既要定义何时拆分，也要定义何时停止。例如，一个记录可以表达一个谓词对一个明确作用域的约束；独立谓词应拆分，同一谓词统一作用于多个对象时不应展开成对象清单。

实例可以进入回归测试，但不应伪装成领域知识进入运行时 Skill。

## 让约束参与生成

产物契约不只是成稿后的检查清单。能够在局部内容决策中判断的要求，应放到产生该决策的位置：选结构时应用结构约束，纳入主张时确认来源与状态，建立关系时检查语义，填充字段时遵守字段契约。不要先放任生成已知不合规的内容，再把修复循环当作默认工作流。

完整产物形成后，检查只有在全局上才能判断的条件、依赖外部证据的条件，以及生成时仍未解决的条件。验证形式和深度取决于任务、失败代价、不确定性与所需证据；简单产物可以只需完成检查，确定性结构可以使用机械验证，只有需要独立归因、比较版本或验证 Skill 行为时才固定候选版本并单独审查。

同一要求只维护一份权威定义。生成、审查和测试可以采用不同使用形态，但不得各自改写成三套规则。

## 测试行为契约，不锁定历史措辞

测试应保护 Skill 必须维持的结构、路由、状态、不变量和可观察行为，而不是把某一版 `SKILL.md` 的标题、句子或关键词永久冻结成接口。只有字符本身就是协议的一部分时，例如 frontmatter 字段、固定状态值、文件路径、机器可读标记或外部约定 token，才应要求字符级一致。

当测试的真实目的属于语义约束时，应优先使用以下层次：

1. 能机械判断的结构和契约直接验证，例如必需路由存在、文件可达、字段合法、状态闭合；
2. 能由稳定语义证据表达的行为，验证必要概念组合或不变量，而不是单个历史短语；
3. 只有运行 Agent 才能判断的行为，使用代表性行为案例验证选择、执行、停止和输出，而不是继续增加关键词断言。

修改 Skill 后若测试仅因等价或更完整的措辞变化而失败，应先判断测试是否错误地把实现文本当成行为契约。不要为了让旧字符串断言通过而牺牲更好的运行时表达，也不要反过来删除仍然有效的行为不变量。

## 把重复 Review 发现回灌到生成阶段

Review 的长期价值不是永久承担同一类修复，而是暴露生成行为还没有内化的稳定缺口。若独立审查反复发现某一类可在局部决策时避免的问题，应把该规则移动到产生问题的决策点，而不是继续依赖尾部 Review 修正。

例如，若 Review 经常发现错误抽象、模式或标志位膨胀、分支增长、包装层堆叠、命名含糊或控制流不清，应分别检查建模、边界选择、抽象选择、状态设计、命名和实现表达的运行时规则。不要简单在 Skill 末尾追加“再检查这些问题”的清单。

开发型 Skill 与独立 Review Skill 应保持不同职责：

- 开发型 Skill 在生成过程中主动避免已知结构和表达缺陷，并在交付前自检当前上下文中已经可见的问题；
- 独立 Review Skill 从外部重新质疑开发者的结构选择、复杂度增长和实现质量，重点发现二阶问题、跨文件问题和作者视角容易漏掉的问题；
- 能稳定前移的规则继续回灌到生成阶段，独立 Review 保留不同视角和全局审查价值，而不是退化成固定返工工序。

如果一个 Skill 只能在最后解释自己为什么写得不好，却不能在相关决策发生时改变行为，应视为执行结构缺口。

## 以证据决定修改方向

测试失败后，先分类原因：

- **知识缺口**：Agent 不知道必要事实或专业规则；
- **路由缺口**：知识存在，但任务没有触发读取；
- **执行缺口**：Agent 能在审计时解释规则，却未在生成时遵守；
- **契约缺口**：要求没有可判定的边界或停止条件；
- **验证缺口**：现有检查不能发现错误。

分别通过 reference、路由、工作流或模板、要求建模、验证器修复。不要默认每种失败都意味着“再加一句提示词”。

## 保持运行时边界纯净

Skill 内只保存终端 Agent 完成任务所需的内容。编写心得、实验过程、原始对话、失败输出、安装说明和维护日志留在仓库级文档或测试体系中。

判断一段内容是否应进入 Skill：删除它若会降低终端 Agent 完成职业任务的质量，则可能属于 Skill；若只会降低以后维护者编写 Skill 的质量，则必须留在 Skill 目录之外。
